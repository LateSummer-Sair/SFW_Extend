权限管理 · 资源 ACL

谁能做什么
一本账就说得清

权限是基板九件事里的一件，也是唯一决定“给不给能力”的地方。它的判据只有一本账 —— 数据根下的 perms.json； 规则也只有一条：先按资源类型的默认分配给位，再让例外条目突破默认。账本里没写的，就是没给；写了空位，就是明确拒绝。

先看看现在的权限 → 我想给别人开权限 被拒时长什么样
01 / 模型

权限模型：谁 × 什么 × 哪一位

一次判定永远由三件事决定：主体（谁在要）、资源（要什么）、位（要读、要写，还是要执行 / 对外）。这三样对上号，结论就是唯一的。

主体三类（外加两种写法）

主体是谁默认位说明
MASTER主人。本地控制台就是主人（控制台命令的调用者按主人算）恒全权任何条目都影响不到他，也不给他写条目
SYSTEM她自己的自主行为：定时唤醒、日常维护、她自己发出去的话A:R / B:RW / C:RWX / E:RWX / T:RWX“没有触发者”的那些调用都归这一类
ALLUSER除主人和她之外的所有人按资源类型的默认分配（见第 06 节）User<QQ号> 与 Group<群号> 的底稿
User<QQ号>某一个具体的人（直接写裸 QQ 号是它的便捷写法）命中例外就按例外给位给单个用户开口子时最常用
Group<群号>某一个群里的所有人命中例外就按例外给位适合把同一件事放开给整个群

层级与顺序

主体层级是 User<QQ号>(3) > Group<群号>(2) > ALLUSER(1)：层级高的先算；同一层级里，后面的条目覆盖前面的。因此给某个人单独开权限时写 User<QQ号> 就够，它天然压过 ALLUSER。

判定的先后是：显式 SYSTEM 标志 → 主人 → 其它主体。SYSTEM 自成一路，只对“她自己的动作”生效，层级同样是 3，不会和普通用户的条目互相干扰。

主人不写进账本

账本里写 MASTER 会被拒收 —— 主体只认 User<QQ号>、Group<群号>、SYSTEM、ALLUSER 四种。主人恒全权，不需要例外，也不接受例外。

她有三条“自主行为”会落到 SYSTEM：定时唤醒、日常维护，以及她自己主动发出去的话。这几类调用没有触发者，所以走 SYSTEM 那条线，而不是某个用户的权限。

模型都在 auth 包里：auth\Acl.java（账本与判定）、auth\Res.java（资源分类）、auth\Bits.java（位运算与格式化）、auth\Caller.java（主体与默认位）。

02 / 资源

资源五类，位只有三个

资源按“要动的是什么东西”分成五类，类别字母就是账本条目里的第一个字符。范围既可以写“整个类”，也可以只写某一个具体目标。

类是什么范围怎么写ALLUSER 默认例子
A本机：SFW 数据根之外的任意本机路径，以及本机进程路径（"" = 整个 A 类）无（一位都不给）A["User123456","D:/share","R"]
BSFW：SFW 运行时目录里的文件（含插件数据根里 files 以外的部分）路径（"" = 整个 B 类）无B["Group121873503","","RX"]
C数据：库的全部内容（db:<库>）、运行期内存状态（mem:xxx）、数据根的 files 目录库名 / mem:xxx / files 下的路径（"" = 整个 C 类）RC["User123456","grouplog","R"]
E外部交互：QQ 平台动作（NapCat 的输入与输出），以及向 SFW 发命令动作名（"" = 整个 E 类）无E["User123456","send_group_msg","X"]
T工具：一把工具的“入口”。执行过程本身不判位，判定只发生在入口工具名（可省 tool: 前缀，"" = 整个 T 类）无T["ALLUSER","<工具名>","X"]

三个位

位只有三个：R 读 / 看；W 写 / 改 / 注册；X 执行或对外（把东西交出去、对外发声）。三者可以任意组合，写成 RWX 这样的串。

""（空）表示一位都没有，也就是拒绝。位的写法大小写与顺序都不敏感（wr 与 RW 同值）；认不出来的位串会被当成“空”处理 —— 拿不准的时候它偏向不放行。

T 类只看 X

工具能不能用只有一条判据：有效位里有没有 X。R 与 W 不参与“能不能调”；同样地，看不到的工具名不会出现在模型可见的工具面里 —— 可见性与能不能调由同一个位决定。

特例：数据根的 files 目录：它是 C 类里的一个特例文件实体 —— 位服从 C 的默认分配（ALLUSER = R、SYSTEM = RWX），但它会按路径式范围命中。所以想单独放开它下面的文件，可以写 C["User<QQ号>","<数据根>/files","RWX"] 这样的条目。

03 / 账本

账本：perms.json

一本账，一个文件，放在数据根下。账本里没有的东西 = 没给；账本里写了空位 = 明确拒绝。这两句就是整套权限的地基。

文件与格式

文件名固定 perms.json，内容是 {"version":3,"entries":[…]}；每一条条目的形态是 类["主体","范围","位"]，其中三格都用双引号包着。

条目字符串会被原样保留、原样打印，所以 ai/acl 里看到的就是账本里的那一行，中间不做二次加工。

它在哪、谁写它

位置是 SairFrameWork\data\AiAgent-V4\perms.json（数据根由配置对象拼出）。写入方是插件自己：授权 / 撤销时由权限面落盘，落盘用的是“先写临时文件再改名”的原子替换，不会留下半截文件。

随仓库的部署脚本会跳过账本，所以升级不会覆盖线上已有的授权清单。

条目形态（照这个写就不会错）

json<数据根>\perms.json（写法示意）
{
  "version": 3,
  "entries": [
    "T[\"User123456\",\"<工具名>\",\"X\"]",        // 只给这个人这一把工具的入口
    "E[\"User123456\",\"send_group_msg\",\"X\"]",    // 允许他发群消息（E 类：外部交互）
    "A[\"Group121873503\",\"D:/share\",\"RW\"]",     // 这个群里的人可读可写 D:/share
    "C[\"User123456\",\"<数据根>/files\",\"RWX\"]", // 让这个人能读写数据根的 files 目录
    "B[\"ALLUSER\",\"\",\"\"]"                      // 全体用户在 B 类：空位 = 明确拒绝
  ]
}

写法要点：类字母是 A / B / C / E / T；主体可以写 User<QQ号>、Group<群号>、SYSTEM、ALLUSER；范围里的空串表示“整个这一类”；位可以写 R / W / X 的任意组合，空串表示拒绝。路径类条目里的路径会做规范化处理，所以同一个目标不会因为斜杠方向不同而变成两条。

改账本前先备份：把 perms.json 复制一份带时间戳的副本再动手，是最省事的退路。形态认不出的条目会被跳过并给一行提示，不会被“猜着用”；已经退休的旧字段也会被忽略。

04 / 查

怎么查：ai/acl 看权限，ai/perm 看好感度

这两个命令名字很像，含义完全不同。一句话记住：ai/acl 管“能不能做”（只读），ai/perm 管好感度数值。

命令干什么会看到什么能不能改
ai/acl 看权限账本：默认分配 + 逐条例外（带主体层级） 两段汇总 —— 一行“默认分配（一条例外都没命中时，按资源类型）”、一行“她自己的默认分配（SYSTEM）”；然后是账本条目逐条列出，空串范围会标注“（空串 = 整个 X 类）”，条目多到超出上限时会写“还有 N 条” 只读
ai/perm 看 / 设 / 重置好感度 好感度数值与榜单口径 能改好感度（不是权限）

好感度不参与任何权限判定：它是一份数据，也是事实块里 caller.favor 的来源，但“能不能做”只由账本说了算。所以给某人放开能力，靠的是写例外条目，而不是把好感度调高。

她在每一轮都能看到你的权限事实：事实块里有三个键 —— caller.kind（你属于哪类主体）、caller.bits（你对五类资源的有效位，也就是结论）、caller.rules（能命中你的例外条目，也就是依据）。她据此判断“这件事能不能答应你”，而这三个键的取值都直接问账本，基板不另算一套。

05 / 改

怎么授权与撤销

控制台不直接改账本：授权、撤销、查询、验算都走她那边的 perm 工具（基板内置工具，随基板走，对主人开放）。

三条路，各管一段

  • 授权 / 撤销 / 查询 / 验算：用她的 perm 工具；
  • 看结果：ai/acl（只读，账本怎么判就怎么显示）；
  • 看数值：ai/perm（好感度，与权限无关）。

授权与撤销会顺手落盘，所以写完就是账本里的既成事实，不用再手动保存。

覆盖还是追加

定位一条条目的键是“主体 + 类 + 规范化范围”：已经有一条同键的，就就地覆盖；没有的，追加到末尾。撤销就是把那一条删掉。

给 SYSTEM 写例外时，工具会额外提醒一行 —— 因为改的是她自己的自主行为，值得确认一次。

可照抄的例子（每条都写“在 ai/acl 里会看到什么”）

目标写这一条在 ai/acl 里会看到
让所有人都能用某一项工具 T["ALLUSER","<工具名>","X"] 账本段多出一行 T["ALLUSER","<工具名>","X"]（主体 ALLUSER，层级 1）
只给某一个 QQ开某一项工具 T["User<QQ号>","<工具名>","X"] 多出一行 T["User…"]（层级 3）；同一工具如果 ALLUSER 另有条目，层级高的先算
允许某人对外发群消息（E 类动作） E["User<QQ号>","send_group_msg","X"] 多出一行 E[…]；E 类默认对 ALLUSER 是“无”，所以这一行就是唯一来源
把 B 类对全体用户关掉（明确拒绝，压过默认） B["ALLUSER","",""] 多出一行范围为空串的 B 条目（会标注“（空串 = 整个 B 类）”），位是空的 ⇒ 拒绝
把某一类资源整类放开读 A["ALLUSER","","R"] 多出整类条目；A 类默认一位都不给，这一行就是“例外突破默认”
让某人能读写数据根的 files（C 类特例） C["User<QQ号>","<数据根>/files","RWX"] 多出一行 C["User…","<数据根>/files","RWX"]；范围是路径式，只命中 files 下面的文件

具体有哪些工具名，看 ai/tools 就知道当前可见的那一批；命令的完整参数见命令参考 · 权限类。

06 / 默认

默认分配与例外：谁说了算

判定只有一条实现：按类默认分配 + 例外突破默认。一条例外都没命中时，位就来自这张“资源类型 → 默认位”的表。

主体A 本机B SFWC 数据E 外部交互T 工具
MASTER全权 RWX（恒定，任何条目都影响不到）
SYSTEM（她自己）RRWRWXRWXRWX
ALLUSER（所有人）无无R无无

这张表就是整套权限的“出厂设置”：她能读本机、能改 SFW 里的东西、数据的读写执行都有、对外动作与工具也都有；普通用户则只有 C 类的读，其余全部为空 —— 想放开哪一格，就写一条命中那一格的例外。

两层“连例外也不开”的受保护资源

  • 第一层：账本自身（perms.json 与它的临时文件）、授权动作本身（mem:acl）、账号凭据（登录态）。只有主人拿得到，连 SYSTEM 也是空的 —— 否则“诱导她自己改权限”就成了绕过主人的路。
  • 第二层：受限配置文件与脚本（按后缀认定的那几类，只对 B 类路径生效）—— 对 ALLUSER 连读都不给，例外也不开。后缀清单是 .json / .ini / .conf / .properties / .yml / .yaml / .toml / .bat / .cmd / .ir / .xml / .env / .key / .pem / .p12，匹配到后缀为止、大小写不敏感，所以 export.jsonl 不算 .json。

为什么默认是“拒绝”

A 类是 SFW 数据根之外的任意本机路径加上本机进程，所以对普通用户一位都不给（连读也不给）。要放开只能写例外。

判定在拿不准时按更严的那一类走：比如路径的真身化不可靠时仍判 A 类，执行本机程序也始终算 A 类。换句话说，“默认拒绝”不是保守，而是这套模型的本意。

07 / 拒绝

被拒时长什么样

拒绝不是一句干巴巴的“没权限”，而是一句可读的说明：它写清缺哪一位、该类默认给什么、当前有效位是什么。它同时也会被算作一次失败，连续失败闸门靠它计数。

text拒绝文案的形态（位名前缀 + 账本原文）
缺 W 位 —— [权限阻断] 需要 <资源> 的 W 位（默认分配 <…>，当前有效位 <…>）

这句话由两段拼起来：前半段是基板 need* 产出的位名前缀（形如 缺 W 位 —— ），后半段是账本给出的原文，开头固定是 [权限阻断] 。工具入口、命令面、面板看到的是同一种形态。

三种拒绝形态都能被认出来

形态长什么样说明
① 现代判据正文里包含 [权限阻断]ACL 内核的产出，唯一现代判据（可能出现在 缺 X 位 —— 之后）
② 兼容识别出现 [auth] 权限阻断旧写法，只用于识别兼容，新的产出文案里不会再出现
③ 信息性前缀以 缺 R 位 —— / 缺 W 位 —— / 缺 X 位 —— 开头基板 need* 的位名前缀；它本身不是拦下的证据，但识别面会保留它

识别用的是“包含 [权限阻断]”而不是“以它开头”，所以前半段有没有位名前缀都不影响判断。为什么这件事值得留意：权限阻断要被算作“失败”，连续失败闸门才数得到它；只认旧串的话，ACL 面的拒绝会被漏掉，她就可能不再补一句正确的回复。

自己怎么确认一句拒绝：拿到那句文案之后，到 ai/acl 里比对三件事 —— ① 该类对该主体的默认分配；② 能命中你的例外条目（事实块里的 caller.rules）；③ 当前有效位（caller.bits）。三者一致，就说明判得没错。

08 / 实现

技术实现（想看代码就从这里进）

权限面集中在 auth 包；另外几处是“接线口”—— 工具入口、拒绝文案产出、失败识别、事实行。

要做的事实现入口
资源命名与分类五类常量与自动判定（路径 / 进程 / 库 / 内存 / 动作 / 工具），含 files 特例auth\Res.java
账本读写解析条目、授权覆盖 / 追加、撤销、原子落盘（先写 .tmp 再改名）auth\Acl.java
唯一判定Acl.bitsOf(caller, res)：按类默认分配 + 例外突破默认；受保护资源对普通用户恒空auth\Acl.java
依据与结论分列Acl.ruleLines() / rulesFor() 给“能命中的例外”，bitsOf 给结论，两者互不代算auth\Acl.java、ctx\CtxBuild.java
接线：工具入口工具能不能用只判 T 类的 X 位；不可见的名字不进模型面tool\Registry.java
接线：拒绝文案Host.need() / needTag() 产出 缺 X 位 —— ，账本原文跟在后面src\sair\v4\skill\Host.java
接线：失败识别Loop.deniedResult() 认三种形态，权限阻断计入连续失败agent\Loop.java
接线：事实行事实块里的 caller.kind / caller.bits / caller.rules 三个键ctx\CtxBuild.java

设计上只有一处判定：面板、命令、事实行都调同一份实现（Acl.bitsOf 与 Acl.source），各自不另算一套；账本自己也只负责“存条目”，不下“有没有权限”的结论。这样 ai/acl 显示的和实际拦你的一定是同一个答案。

09 / 排错

常见误用与排错

权限问题大多来自三件事：写错了类、给错了位、或者压根没写。下面这几条按“先看什么”的顺序排，照着走一般就找到了。

现象先看什么原因与处理
写了例外但不生效 ai/acl 里有没有那一行、位是不是你要的 ① 主体写错：MASTER 会被拒收，写成 User<QQ号> 就好；② 类写错：T 是工具、E 是外部交互动作；③ 位写空就是拒绝，建议再确认一次那一格。
同一资源有人能用、有人不能 事实块里的 caller.rules（能命中的例外） 层级高的先算：User(3) > Group(2) > ALLUSER(1)，同级里后面的覆盖前面的。给某个人单独开时，User<QQ号> 那条才压得住群条目。
改了账本要不要重启 用 ai/acl 再问一次，看判定有没有变 账本在首次判定时装载，另有显式重载口；取值与判定共用同一份实现，文件变了会被重读。手改文件之后，建议用 ai/acl 再问一次：显示对了，判定就是对的。
条目形态写坏 那一行提示 形态认不出的条目会被跳过并给一行提示，不会影响其余条目；部署脚本遇到形态非法也会明确报出来。写完照一下 第 03 节的样例即可。
她“答应不了”某件事 那句 [权限阻断] 说明 说明里点明了资源、该类默认分配与当前有效位。按第 07 节的三步对一遍，就能确认是差一条例外，还是差一个位。
不确定谁能动什么 ai/acl 开头那两段“默认分配” 先读默认、再读条目：没写的一律按默认，而默认基本是拒绝。这样推出来的结论与实际判定同源。

相邻内容在别处：本页只写基板的权限模型、账本、命令与实现口。命令的完整参数见命令参考 · 权限类；键的逐条含义见配置键面 —— 权限不在配置里，它是一本独立账本。外挂扩展层具体有哪些单元、各自做什么，不在本页范围。
