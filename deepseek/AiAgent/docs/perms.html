权限管理 · 技能管控表

谁能用什么
一张表就说得清

权限是基板九件事里的一件，也是唯一决定“给不给能力”的地方。它的判据是一份份按归属分散的权限文件 —— 基板内置工具的那份在数据根下的 perms-core.jsonc， 每个技能自己那份在 skills\<技能名>\perms.jsonc。装载时它们合并成一张表，也就是控制台里看到的技能管控表。这张表分三个域：技能（谁能用哪个 op）、数据（谁能改、谁能读哪类数据）、文件（谁能碰哪些路径）；每个域各看自己那一层。 规则都写成 ["键"]: [身份…] 的中括号形式，一个键也能这么写；// 开头的整行是注释。没列到时按该域自己的默认值收尾 —— 技能不能、数据能读不能改、文件不能碰；注意区分：写出来了却给一个空身份数组不是“没列到”，它是一条“谁都不给”的决定（那两个域的读侧因此就是不能读）。技能目录里没有那份 perms.jsonc，它的全部 op 对普通用户就一律不授权。

01 / 模型

权限模型：域 × 每一层 → 允许 / 禁止 / 空

一次判定先看你问的是哪一域：技能、数据、还是文件。每一域各有自己的层 —— 技能只有允许与禁止两层（Run / Ban），数据与文件分“改”“读”和“谁都不能”（Run / Read / Ban）。更具体的键优先，同一把键上禁止压过允许，只有“谁都没给决定”时才按该域的默认值收尾。

三域与各自的层

词表是钉死的：技能只有 Run 与 Ban 两层（它不设“读”，读归数据与文件两域）；数据与文件各有 Run / Read / Ban 三层。在某一域里写它没有的那一层（例如给技能写 Read，或者把层名拼错），整层被忽略并点名，不会生效。

域键是什么有哪些层没列到时
Skillop 名（工具名 或 工具名.动作名）Run（能用）、Ban（不能用）不能用
DB数据类别（下面「数据键」那一节逐个列）Run（能改）、Read（能读）、Ban（谁都不能）改：不能改；读：能读（全表唯一默认放开的一处）
File路径（目录写成末尾带斜杠 = 整棵子树）Run（能改）、Read（能读）、Ban（谁都不能）改：不能改；读：不能读

同一域里，更具体的键优先：pref.donation 比 pref 具体，文件按最长路径优先（子目录里的禁止压过父目录里的允许）。同一把键上 Ban 压过 Run 与 Read；同一个键在一份文件里写了多处，取并集。

三种身份（外加两种写法）

身份是谁表里的结论说明
MASTER主人。本地控制台就是主人（控制台命令的调用者按主人算）恒全权不写进表里，任何条目都影响不到他
SYSTEM她自己的自主行为：定时唤醒、日常维护、她自己发出去的话恒全权同样不写进表里；“没有触发者”的那些调用都归她
ALLUSER除主人与她之外的所有人只能用表里放行的 opuser:<QQ号> 与 group:<群号> 的底稿
user:<QQ号>某一个具体的人（直接写裸 QQ 号是它的便捷写法）与 ALLUSER 各算各的给单个用户开口子时最常用
group:<群号>某一个群里的所有人与 ALLUSER 各算各的适合把同一件事放开给整个群

结论只有三种，按域收尾

每一域只问一件事：这个域上的这个键，给不给这个身份。答案三种 —— 允许（Run，数据与文件另有 Read）、禁止（Ban）、空。“空”是两回事：没列到的时候按上面三域表最后一列收尾；写出来了却是一个字面空数组（["sent"]: []）则是一条决定 —— 它表示“列出来了，但谁都不给”，判定到这里就停，不再回落到更宽的键、也不吃该域“没列到”的默认值。所以数据与路径两域的读侧一旦写成空表，结论就是不能读，不会被“数据默认能读”那一口吃掉。

优先级 Ban > Run / Read > 空：同一把键上，只要这个身份命中任何一条 Ban 就拒；没有 Ban，才轮到看有没有给他允许。

主人与她不写进表

身份键的规范写法只有三种：user:<QQ号>、group:<群号>、ALLUSER；裸 QQ 号等于 user:<QQ号>。另外还接受几种等价写法：全体 / 所有人 / 全部 等于 ALLUSER，qq: 前缀等于 user:，用户… 等于 user:，群号… / 群… 等于 group:。主人（MASTER）与她本人（SYSTEM）恒全权，不受这张表约束：手写进文件里的那几行整行忽略 —— 不报错、不生效，也不占“已经声明过”的位置；在控制台敲写命令时，这两个身份会被直接回绝，回的原话分别是“主人恒全权，不需要写进表里”与“她自己恒全权，不需要写进表里”。

她有三条“自主行为”落到 SYSTEM：定时唤醒、日常维护，以及她自己主动发出去的话。这几类调用没有触发者，所以按她本人算，而不是按某个用户的权限。

默认值里唯一放开的一处：DB 的“读”在没列到时是能读 —— 全表只有这一处默认放开。所以装载时会把“没有显式 Read 声明、按默认能读”的类别逐个点名列出来，敲 ai/perm 就能看到那一行；要把某类数据关掉，就在 DB 的 Ban 里写上它。

模型都在 auth 包里：auth\Acl.java（合并装载、管控表与判定）、auth\Ops.java（op 清单）、auth\Caller.java（身份）、auth\Auth.java（权限面出口）。

02 / 资源

资源没有“位”这回事

新模型里不再有“按资源分类分配读 / 写 / 执行”这套 —— 资源不分等级，也没有按类给读 / 写 / 执行的分配。那点位置感，被“能不能用某个 op”整个替掉了。

对主人与她本人

资源完全可见、可改、可执行 —— 基板自己的库、数据根里的文件、对外的平台动作都在这一侧，不需要任何条目，也不受表影响。

对 ALLUSER

资源是一个黑盒：读 / 写 / 执行唯一的路是技能（工具）这条手脚。所以“他能做什么”就等于“表放行了他哪些 op”。

数据根的 files 目录：它也是一份普通资源，没有自己的位。想让某人能看、能写它下面的东西，路只有一条 —— 在 Run 块里给文件那一组的对应动作补上他的身份；这一条会写进这个 op 归属的那份权限文件（回执里会写清是哪一个）。

03 / 权限文件

权限文件：按归属分散

不再是单独的一份账本，而是谁的工具就写在谁那里：基板内置工具的那份放在数据根下，每个技能自己那份放在它的目录里；装载时合并读成一张表。表里没有的 op = 没给；列出来了却给了一个空身份数组 = 同样没给。这两句就是整套权限的地基。

文件与格式

两份文件名都固定：基板内置工具那份是 perms-core.jsonc，技能那份是 perms.jsonc。层次固定四层：最外面是 version（这一版写 6）与 _readme，接着是域（Skill / DB / File），每个域里是它自己那几层（技能是 Run / Ban；数据与文件是 Run / Read / Ban），层里是规则 —— 规则层的键一律写成中括号数组 ["a", "b"]，里面只有一个键时也带括号（["weather"] 与裸写 "weather" 等价，读出与重排都按带括号的那一种）。

规则的值就是身份数组。以 // 开头的整行是注释，写在内容的前一行，基板读之前整行丢掉。写它有两条入口，都只对主人开放：控制台的 ai/perm 这一族命令，以及她手上那个内置的 perm 工具（授权、封禁、撤回、重排都当场落盘，落盘用的是“先写临时文件再改名”的原子替换，不会留下半截文件）。

它在哪、谁写它

落点按归属分：数据根下那份管基板内置工具（不属于任何技能的 op 与路径都写它），skills\<技能名>\perms.jsonc 管这个技能自己提供的工具。技能那份里只许写它自己的 op，DB 块里只许写属于它的数据键，File 块只许写在基板那份（路径属于部署，不属于某个技能）。真正动笔的两条入口都只对主人开放：控制台的 ai/perm 那一族命令，与她手上那个内置的 perm 工具；其它地方只读，装载、判定、查看都不写。

任何一次写命令都会把已有的权限文件按这一版的形状重排一遍（一份文件只写它自己的东西）。重排出来的文本与文件里现有内容逐字节相同，就跳过这一次写。所以回执里的“已写入 X”指的是这条规则归属的那份文件，不等于“只有 X 被写”。

随仓库的部署脚本会跳过这些权限文件（按文件名跳过，所以技能目录里那几份也一起跳），所以升级不会覆盖线上已有的授权清单。

文件的形态（照这个写就不会错）

json<数据根>\skills\<技能名>\perms.jsonc（写法示意）
{
  "version": 6,
  "_readme": "…（这是什么文件、怎么读）…",

  "Skill": {
    // ── 查某城市（weather）
    ["weather.report"]: ["ALLUSER"]
  },

  "DB": { },
  "File": { }
}

写法要点：域在最外面一层（Skill / DB / File），域里是它自己那几层（技能只有 Run / Ban；数据与文件是 Run / Read / Ban；在某一域里写它没有的那一层、或者把层名拼错，整层忽略并点名），层里是规则 —— 规则层的键一律带中括号，["a"] 与 ["a", "b"] 都这么写，值就是身份数组，一个键可以一次写几个（["memory.remember", "memory.recall"]: ["ALLUSER"]）。以 // 开头的整行是注释，写在内容的前一行，基板读之前整行丢掉。身份键的规范写法只有 user:<QQ号> / group:<群号> / ALLUSER 三种，裸 QQ 号等于 user:<QQ号>；另外还接受几种等价写法：全体 / 所有人 / 全部 等于 ALLUSER，qq: 前缀等于 user:，用户… 等于 user:，群号… / 群… 等于 group:。_readme 那一行只给人看，基板读的时候会跳过。技能那份文件只认它自己提供的工具（以及属于它自己的数据键），写了别人的、或者基板内置工具的 op，那一条会被忽略，并在启动时点名一行；也没有一份给人看的旁注 Markdown，能看、能改的就是这些 .jsonc 文件。

改文件前先备份：把 perms-core.jsonc 与要用到的技能目录里的 perms.jsonc 各复制一份带时间戳的副本再动手，是最省事的退路。认不出的写法会被原样留着并点名，而且一律不生效，不会被“猜着用”。

数据键：就那几类，认不出的一律点名

DB 域的键是数据类别。表级就是表名：dialog、grouplog、memory、note、pref、emotion、group_impression、sticker、favor、favor_event、alarm、task、skill_index、sent。表里还有更细的子类与一批 kv.* 抽屉，一共 35 类。

数据键怎么认它归谁
memory长期记忆那一张表技能「记忆」
memory.impressionmemory 里来源是印象蒸馏的那些行技能「印象蒸馏」
notenote 里由知识笔记写下的那些行技能「知识笔记」
note.correctnote 里来源是修正记录的那些行技能「修正记录」
note.experiencenote 里来源是经验蒸馏的那些行技能「经验蒸馏」
pref.donationpref 里键名以可配置前缀（默认 donation:）开头的那些行技能「捐赠」
sticker表情包那一张表技能「表情包」
emotion情绪那一张表技能「情绪」
group_impression群印象那一张表技能「群印象」
以上之外的表级键（dialog / grouplog / favor / favor_event / alarm / task / skill_index / sent 等），以及全部 kv.* 抽屉，都归基板 —— 只许写在 perms-core.jsonc 里。

写到技能文件里的数据键不属这个技能，就是越界：那一条被忽略、启动时点名一行（DB 块与 File 块同一口径）。另外三条不是数据键 —— 附加媒体、轮次、聊天窗口那三段是上下文事实行的前缀，不落任何库，写进 DB 块会被当成认不出的键点名。认不出的键一律不生效，方向只会更严。

路径键：目录末尾带斜杠 = 整棵子树

File 域的键是路径，正斜杠与反斜杠都写得进（装载时会归一化：反斜杠统一成正斜杠、去掉重复的斜杠、解掉 . 与 ..；Windows 上比大小写不敏感）。目录写成末尾带斜杠就是它的整棵子树，不带斜杠就是那一个文件。判定按最长路径优先：["D:/data/"] 放行、["D:/data/runonly/"] 禁止，那么后者那一棵树就是碰不了。不认通配符 —— 要整棵子树就把目录写成末尾带斜杠，别写 *。

路径块只写在基板那份：路径属于部署，不属于某个技能。技能目录里的 perms.jsonc 里写了 File 块，整块被忽略并点名一行；而且重排那份文件时它会被丢掉 —— 写出来的每一份文件，都必须能被读回来时不报越界。

04 / 查

怎么查：ai/perm 看表，ai/favor 看好感度

这两个命令名字很像，含义完全不同。一句话记住：ai/perm 管“能不能做”（技能管控表），ai/favor 管好感度数值。旧名字 ai/acl 已经退休，只留一句指路。

命令干什么会看到什么能不能改
ai/perm 看合并后的技能管控表：技能、数据、文件三个域，每个域里是自己的层 整张表逐条原文 + 一行摘要（几 Run、几 Ban、覆盖多少个 op、有没有认不出的键）+ 数据与文件那两个域的规则行（域 → 层 → 键，同一个键先取并集再打印）+ 一行“未声明 Read、按默认能读的类别” + 装载汇总一行 + 来源汇总（core 几条、技能几份共几条，再逐份列出路径与条数）+ 一行「另有 N 个动作没在表里（= 未授权）」+ 一段怎么用；一份权限文件都没有时会直说“一切未授权”，并提示敲 ai/perm run 开口子 只读（run / ban / db / file / revoke / gen 才写盘，而且只有主人能跑）
ai/perm list [op] 按 op 看谁能用 不给 op 就把表里每个 op 逐行列全；给一个 op 就只看它那一条 只读
ai/favor 看 / 设 / 重置好感度 好感度榜单（前 20 名）与单人的数值、档位 能改好感度（不是权限）

好感度不参与任何权限判定：它是一份数据，也是事实块里 caller.favor 的来源，但“能不能做”只由技能管控表说了算。所以给某人放开能力，靠的是在对应那一层里补一个身份，而不是把好感度调高。

她在每一轮都能看到你的权限事实：事实块里有三个键 —— caller.kind（你属于哪类身份）、caller.ops（你能用的 op 清单，也就是结论；恒全权写 "ALL"，一个都没授权写 []）、caller.rules（能命中你的管控表条目，也就是依据）。她据此判断“这件事能不能答应你”，而这三个键的取值都直接问权限面，基板不另算一套。

05 / 改

怎么授权与封禁

控制台不直接改文件：看表、授权、封禁、撤回、重排、重读都走 ai/perm 这一族命令，写命令只有主人能跑。写进去落到哪一份由归属决定 —— 回执里会写明是哪个文件。

八条子命令，各管一段

  • 看表：ai/perm（整张表）、ai/perm list [op]（按 op 看谁能用）；
  • 授权：ai/perm run <op> <身份…>，落进 Skill 那一层的 Run，并写进该 op 归属的那份文件（回执里写明，例如 已授权：weather ← ALLUSER（已写入 …））；
  • 封禁：ai/perm ban <op> <身份…>，写的是 Skill 那一层的 Ban；
  • 数据：ai/perm db run|read|ban <数据键> <身份…>，写的是 DB 这一域的对应层（run = 谁能改、read = 谁能读、ban = 谁都不能）；
  • 路径：ai/perm file run|read|ban <路径> <身份…>，写的是 File 这一域的对应层（目录末尾带斜杠 = 整棵子树）；路径里含空格时整段用一对双引号包起来，没配对会直接拒掉；
  • 撤回：ai/perm revoke <键> <身份>，键会自动认它属于哪一块（op / 数据 / 路径），一次把这个身份在该键上的全部条目摘干净；
  • 重排：ai/perm gen，只在已有的权限文件里重排与补注释（不新建文件），并把“这些 op 还没有权限文件（= 不授权）”列出来；
  • 重读：ai/perm reload，外面手改了权限文件之后，重新合并装载一遍（顺手重新取一次工具归属）。

授权与封禁写完即落盘、当场生效，不用再手动保存，也不用重载。

覆盖还是追加

定位一条规则的键是“域 + 层 + 键 + 身份”：同一个键上同一个身份只留最后写的那一条（先撤旧的再写新的），同一行里其余的身份原样留着；同一个键在两个地方都写了，判定时取并集（同名键上 Ban 照样赢）。

gen 会把已有的那几份权限文件重新产出一遍 —— 手改过的排版会被它排回来，而哪些身份在各自那一层里会原样保留。它不新建文件、不发明新的数据或路径条目、也不给宽身份新增授权；技能文件里不会写出路径块。

身份写法认不出来时，一个字都不会写 —— 先全验、再动文件。控制台写命令里写 MASTER 或 SYSTEM 会被直接回绝（他们恒全权，不用写进表）。

可照抄的例子（每条都写“敲完会在 ai/perm 里看到什么”）

目标敲这一条在 ai/perm 里会看到
让所有人都能用某一项工具 ai/perm run weather ALLUSER Skill 的 Run 里多一条 ["weather"]: ["ALLUSER"]；这一条写进了「天气查询」技能目录里的 perms.jsonc
只给某一个 QQ开某一项工具 ai/perm run weather 123456 那一行的身份数组里多一个 user:123456；原来的 ALLUSER 不受影响，两个人各算各的
只放开一把工具里的某一个动作 ai/perm run memory.remember 123456 Skill 的 Run 里多一条 ["memory.remember"]: ["user:123456"]；这把工具别的动作照旧没给
放开某一类数据给别人改 ai/perm db run pref.donation ALLUSER DB 的 Run 里多一条 ["pref.donation"]: ["ALLUSER"]；命中之后还要看那一行是不是他自己的
让某一类数据谁都不能读 ai/perm db ban sent ALLUSER DB 的 Ban 里多一条 ["sent"]: ["ALLUSER"]；这一类也就不再出现在“按默认能读”的清单里
放开一整棵目录子树 ai/perm file read "D:/data/share/" ALLUSER File 的 Read 里多一条 ["D:/data/share/"]: ["ALLUSER"]；末尾那个斜杠就是“整棵子树”，路径含空格所以要加引号
把某一项能力对某个人关掉（压过任何放行） ai/perm ban weather 123456 Skill 的 Ban 里多一条 ["weather"]: ["user:123456"]；同一把键上 Ban 压过 Run
把已有的权限文件重排 ai/perm gen 已有的那几份权限文件被按域、层、键重排一遍；每一层里哪些身份原样保留。它不新建文件，还会列出“这些 op 还没有权限文件（= 不授权）”
把某个身份整个撤回 ai/perm revoke weather 123456 那一行里不再有 user:123456；若一行里因此一个人都不剩，整条就被删掉（不会留一条空壳）

具体有哪些工具名与动作名，看 ai/tools 就知道当前可见的那一批；命令的完整参数见命令参考 · 权限类。

06 / 摆法

表怎么摆：分组、释义、身份数组

层次的形状固定四层：最外面是 version 与 _readme，接着是域（Skill / DB / File），域里是它自己那几层（技能只有 Run / Ban；数据与文件是 Run / Read / Ban），层里是规则 —— 键写成中括号数组，值写成身份数组。

层长什么样基板怎么读
version"version": 6读到上一版的 5 会按旧语义读并留一行提示；比这一版新也留一行提示，认得的字段照读
_readme一段给人看的用法说明不参与任何判定
域Skill / DB / File拼错的域名整块忽略并点名
层Run / Read / BanSkill 只有 Run / Ban；另外两域三个都有。拼错的层名整层忽略并点名
规则键["a", "b"]（op / 数据类别 / 路径）键数组合成一个键读进来；["a"] 与裸写 "a" 等价，重排只输出带括号的那一种。认不出的键点名且不生效
身份数组["ALLUSER"] 或 ["user:123456","group:123456"]数组里有这个身份就算命中；空数组是一条“谁都不给”的决定（按域收尾，见第 01 节），不再回落到更宽的键

三道闸门：技能 / 数据 / 文件

技能门

先判一次“这把工具交不交到他手上”：整把工具那一条放行，或者它任一动作放行，这把工具才会出现在这个身份的调用者面前 —— 没放行，对他来说它在工具面里根本不存在。工具内部每个动作再判一次自己的 op，两道都过了才真的执行。

数据门与文件门

数据门在通用库口上：改一类数据要先过那一域的 Run，命中之后还要看这一行是不是他自己的；读一类数据过 Read（没声明时按默认能读，写成空表则不能读）。

文件门在碰路径的地方：改路径过 Run、读路径过 Read，按最长路径优先 —— 子目录里的禁止压过父目录里的允许。

表里列出哪些 op、按什么顺序、配什么释义，都以 ai/perm gen 重排出来的为准；它按技能装载时声明的 op 清单给出分组、释义与顺序，清单只增不减地跟着技能走。写一个注册表里还没有的动作名，本身是可以的：在基板那份文件里写精确键（["perm.nowhere"]）就是预先授权 —— 写工具名的键只覆盖装载时已经注册的动作，而精确键一旦有人原样拿这个动作名来问判定就会命中，主人可以这样提前给一个将来才会注册的动作开权限。技能那份文件则是另一条口径：注册表里没有的动作连装都装不进去，那一条会被整条丢弃并点名；写了不属于它的 op 同样会被忽略并点名。

没列到，就是没给

表里没提过的键，对普通用户一律按该域“没列到”的默认值走。装载新技能会让 op 清单变长，但新技能目录里还没有那份 perms.jsonc 时，它的 op 一样不授权 —— 要开就敲 ai/perm run。

只放行一个动作时，另外那些动作照旧没给 —— 所以“允许他记一笔”与“允许他翻别人的记忆”能分成两件事。工具级的那一条键只覆盖它已经注册的动作（没注册过的动作不会被旧授权顺手放行）。

键怎么对上：宽的、更具体的

判定时先把覆盖这个键的规则从最具体往最宽排一遍，看第一把给出决定的：精确同键最具体；数据按点分往上看（pref.donation 比 pref 具体）；路径按最长优先。更具体的键没给这个身份任何决定时，才落到更宽的键。

数据与文件两域的宽键按它自己的身份表命中 —— 以后新登记的、以及表里的键空间还没一一列出的子键，都会被宽键照常判（例如 DB 里写了 ["pref"]: ["user:123456"]，那么 pref 底下那些更细的键对这个身份也按这一条判）。

技能那一域不一样：写工具名的宽键只覆盖装载时这把工具已经注册的动作；而且在技能文件里，没注册过的动作连装都装不进去 —— 那一条会被整条丢弃并点名，以后技能新加的动作也不会被旧授权顺手放行（这正是“默认拒绝”的兜底）。

只有一件事另算：这个键完全没有得到任何决定，而且没有被任何一个已知的宽键覆盖，才会得到“不认识的权限键”这句拒绝 —— 它对应的就是装载时已经点过名的那些认不出的键。

同一把键上命中多条时取并集（要收窄只能用 Ban）。另外，数据那一域的读判定里，“显式写下的空身份表”与“Ban”一样会拦住读 —— 只有确实没声明的键才吃“默认能读”那一口。

早先那张统一的权限表已经按归属拆到各技能目录与 perms-core.jsonc 了 —— 现在没有单独的一份账本，看的时候是合并视图。旧格式照读：上一版的嵌套写法与那份旧的统一表都还能读进来，装载时会提示建议敲 ai/perm gen 重排一次；更早那版按资源分类的权限账本，启动时还会读一次做迁移（只读不写，条目里带 X 的转成允许，按资源分类的那几行在新语义里没有意义、直接略过）。老文件里没写 DB / File 两域时，就按该域“没列到”的默认值走 —— 不会因为“没写”而放宽。

07 / 不可用

不可用时长什么样

不可用不是一句干巴巴的“没权限”，而是一句可读的说明：它写清挡在哪一域、哪一层。它们同时也会被算作一次失败，连续失败闸门靠它计数。

text不可用文案的几种形态
[权限阻断] 「weather」在技能管控表的黑名单里
[权限阻断] 「weather」没有授权给你（未列到 = 未授权）
[权限阻断] 这类数据（sent）你不能读
[权限阻断] 这条记录不属于你（只能改你自己那一份）
[权限阻断] 这个路径不在允许范围（D:/…）
场景文案形态
技能：没授权[权限阻断] 「memory.remember」没有授权给你（未列到 = 未授权）
技能：列出来了但空表[权限阻断] 「memory.remember」没有授权给你（列出来了，但谁都没给）
技能：被禁[权限阻断] 「memory.remember」在技能管控表的黑名单里
数据：不能改[权限阻断] 这类数据（memory）你不能改 —— 只有主人与她本人能改
数据：不是他的行[权限阻断] 这条记录不属于你（只能改你自己那一份）
数据：不能读[权限阻断] 这类数据（sent）你不能读
路径：不能碰[权限阻断] 这个路径不在允许范围（D:/…）
键认不出[权限阻断] 不认识的权限键「xxx」（装载时已点名）

每一句都以 [权限阻断] 开头，尾部说明是哪一层挡的；文案本身不透露白名单里有什么（路径那一句只说“不在允许范围”）。这个前缀一字不改 —— 这一版只是在它后面补了分层说明。工具入口、命令面、面板看到的是同一种形态。

三种形态都能被认出来

形态长什么样说明
① 现行判据正文里包含 [权限阻断]权限面的产出，唯一现行判据
② 兼容识别出现 [auth] 权限阻断旧写法，只用于识别兼容，新的产出文案里不会再出现
③ 历史前缀以 缺 R 位 —— / 缺 W 位 —— / 缺 X 位 —— 开头早期基板留下的前缀，新口径已经不再产出；识别面留着它，只为不把历史文案误认成成功

识别用的是“包含 [权限阻断]”而不是“以它开头”，所以前面带不带那几个字都不影响判断。为什么这件事值得留意：权限阻断要被算作“失败”，连续失败闸门才数得到它；只认旧串的话，权限面的拒绝会被漏掉，她就可能不再补一句正确的回复。

自己怎么确认一句不可用：拿到那句文案之后，到 ai/perm 里对两件事 —— ① 这个 op 在他能用的清单里吗（事实块里的 caller.ops）；② 有没有一条 Ban 命中他（caller.rules）。两者一致，就说明判得没错。

08 / 实现

技术实现（想看代码就从这里进）

权限面集中在 auth 包；另外几处是“接线口”—— 工具入口、命令面、失败识别、事实行。

要做的事实现入口
合并装载Acl.loadMerged 把 perms-core.jsonc 与各技能目录里的 perms.jsonc 读成一份视图：// 整行注释先丢掉，技能文件里的 op 越界、数据键越界、路径块三种情况都忽略并点名一行；认不出的键一律点名且不生效auth\Acl.java
文件读写解析三域四层、授权 / 封禁 / 撤回；按归属分文件写回（技能 op → 该技能目录，其余 → core），重排时技能文件不产出路径块、数据块只在真有规则时写；逐字节相同则跳过写，落盘是原子替换（先写 .tmp 再改名）auth\Acl.java
op 清单技能装载时声明工具名与动作名；重排时的分组、释义与顺序都从这份清单来，工具级的那条键覆盖它已注册的动作auth\Ops.java、auth\OpList.java
判定：技能Acl.allow(caller, op)：先看 Ban、再看 Run、都没有就是未授权；主人与她本人直接放行auth\Acl.java
判定：数据Acl.dbDeny(caller, 数据键, 行归属) 管改（命中后还要比这一行归谁）；Acl.dbReadDeny(caller, 数据键) 管读（没声明时能读，显式空表则是不能读）auth\Acl.java
判定：文件Acl.fileDeny(caller, 路径, write)：write 为真看 Run、为假看 Read，按最长路径优先auth\Acl.java
域内怎么比同一域里把覆盖这个键的规则从最具体往最宽过一遍，第一把给出决定的说了算；同一把键上 Ban 先于允许，身份取并集auth\Acl.java
结论与依据分列Acl.opsFor() 给“能用哪些 op”（结论），权限文件里的条目配合 ctx\CtxBuild.java 给“能命中他的条目”（依据），两者互不代算auth\Acl.java、ctx\CtxBuild.java
接线：工具入口整把工具或它任一动作放行，工具才可见；调用时入口再判一次，工具内部每个动作又判一次tool\Registry.java
接线：通用库口六库的读写与整库动作都先过数据那一道（整库动作把它覆盖到的每一类都过一遍），行归属按类别各自映射成 user:<QQ> / group:<群号>Builtins.java
接线：文件口本地文件改写、外链地址产出、导出与导入这几条取路径的写口都过路径那一道Builtins.java、qq\Relay.java、qq\Api.java
接线：命令面看表用 ai/perm，写表用 run / ban / db / file / revoke / gen；旧名字只留一句退休指路term\Cmd.java
护栏：技能不能给自己开口子skill_write 的写入路径拒收 perms.jsonc，回的原话是“拒绝写入 perms.jsonc：… —— 权限文件（谁能用这个技能）只能由主人用控制台 ai/perm 写，技能不能给自己开口子。”Builtins.java
接线：失败识别Loop.deniedResult() 认三种形态，权限阻断计入连续失败agent\Loop.java
接线：事实行事实块里的 caller.kind / caller.ops / caller.rules 三个键ctx\CtxBuild.java

判定只有一套实现：命令面、工具入口、通用库口、文件口、事实行都问同一份实现（Auth 与 Acl 上那几个入口），各自不另算一套；权限文件这一层也只负责“存规则”，不下“能不能用”的结论。这样 ai/perm 显示的和实际拦你的一定是同一个答案。

09 / 排错

常见误用与排错

权限问题大多来自三件事：op 写错了、身份写错了、或者压根没写。下面这几条按“先看什么”的顺序排，照着走一般就找到了。

现象先看什么原因与处理
给了身份但不生效 ai/perm list <op> 里有没有他 ① op 写错：整把工具写 工具名，单个动作写 工具名.动作名；② 身份写错：在控制台写 MASTER 与 SYSTEM 会被直接回绝（手写进文件里则是整行忽略、不生效），写成 user:<QQ号> 就好；③ 同一个 op 上他命中了 Ban，那就先 ai/perm revoke 再放行；④ 这个 op 属于某个技能，而它的目录里还没有 perms.jsonc —— 走 ai/perm run 就会顺手建起来。
同一项能力有人能用、有人不能 事实块里的 caller.rules（能命中他的条目） 一个人身上的条目与一个群上的条目各算各的，Ban 压过 Run。给某个人单独开的时候，先确认没有一条更宽的身份（ALLUSER）把他封了。
改了表要不要重启 用 ai/perm 再看一次，或对某个 op 敲 ai/perm list 走 run / ban / db / file / revoke / gen 写完即生效；只有外面手改了权限文件（perms-core.jsonc 或某个技能目录里的 perms.jsonc），才需要敲一次 ai/perm reload。
表里多出一条不认识的写法 那一行点名 认不出的键会原样留着并点名，而且一律不生效（不影响其余条目）；照第 06 节的四层形状改回来，或者敲一次 ai/perm gen 重排。
技能里给别的能力开了口子 启动时那一行 [acl] 越界忽略：… 技能那份文件只认它自己提供的工具与数据键：写了别人的、或者基板内置工具的 op，整条都会被忽略并点名一行，原句形如 [acl] 越界忽略：技能「天气查询」的 perms.jsonc 里写了不属于它的 op「send.group」（属技能「消息发送」）—— 这一条不生效。写数据键越界、或者写了 File 块，也是同一句话的两种变体（数据键那一条不生效、路径那一整块不生效）。要开就写到那个键归属的那份文件里。
技能好像想给自己开权限 skill_write 的回执 技能的写入路径碰到 perms.jsonc 会被直接挡回，回一句“权限文件（谁能用这个技能）只能由主人用控制台 ai/perm 写”—— 所以技能没法给自己开口子。
她“答应不了”某件事 那句 [权限阻断] 说明 说明里点明了是哪一域、哪一层挡的。按第 07 节那张表对一遍，就能确认是差一条允许，还是被一条 Ban、一条行归属、或者一个路径挡住了。
不确定谁能动什么 ai/perm 打出来的整张表 先读禁止再读允许：没写到的一律按该域的默认值算（技能不能、数据能读不能改、文件不能碰）。这样推出来的结论与实际判定同源。

相邻内容在别处：本页只写基板的权限模型、权限文件、命令与实现口。命令的完整参数见命令参考 · 权限类；键的逐条含义见配置键面 —— 权限不在配置里，它是一份份独立的小文件，按归属分散在数据根与各技能目录里。外挂扩展层具体有哪些单元、各自做什么，不在本页范围。
