SKILLS

自己写一个技能

上一节说的是"已经装上的有什么"。如果你的想法不在那 32 条里，这一节就派上用场了 —— 写一个技能差不多是"一个目录、一份说明、一个类"，我们从头走一遍。

技能是什么：外挂层里的一个目录

技能是外挂层的最小单位，就是 data\skills\ 下面的一个目录。它跟基板的关系很松：基板不核对"应该有哪几个技能"，也不假设外挂层一定存在 —— 把整个 data\skills\ 删掉，基板照样启动、照样对话，只是工具少一些、钩子没人接。

反过来说，技能也改不动基板的骨架与判定。它通过宿主拿到一个只读的能力面，用基板已经有的东西做事。一个技能能提供两样东西，也可以只给其中一样：

工具，给模型用

在 md 里声明 tool:，再写一个入口类，模型在对话里就多了一件事可以做。它会在每轮的能力索引里出现，需要的时候模型自己调，返回值回到对话里接着往下走。

钩子，挂在时机上

进站消息、出站正文、定时心跳、上下文注入、好友申请与群邀请 —— 挑一个时机挂上去，在旁边做事。这类技能可以不提供工具，模型那边完全看不到它。

也可以只有一份说明

只放一个 md、不写 .java，它也算一个技能：出现在清单里、能被读到，只是没有可执行的部分。适合先把位置占住、把想法写下来。

目录与文件：三样东西

以 hello 为例，目录名就是技能名，里面放三样东西（后面两样可选）：

textdata\skills\hello\
hello.md      声明 + 说明书（文件名与目录同名）
prompt.md     可选：写给模型的文案、这个技能自己的配置
Hello.java    可选：实现类
文件放什么
<技能名>.md开头一段 front matter 做声明，下面写给人看的说明书（ai/skill read 会把声明与正文一起打出来）。文件名与目录名不一致会加载失败，日志里也会说清原因。
prompt.md面向模型的文案，以及这个技能自己的配置（阈值、示例、话术）。它是普通文本文件，改完保存就生效，不用重新加载技能。
*.java实现类，运行期编译，不在磁盘上留 .class。一个目录可以放多个源文件，不写 package，按默认包编译。

front matter 里可以写什么

键写什么
name技能名，与目录名保持一致。
description一句话说明它是干什么的，清单里显示的就是这一句。
tool可选。给模型的工具名；不写就等于"这个技能不提供工具"。工具名建议用英文、数字与下划线，把中文留给技能名。
hooks可选。要收的事件，例如 on_message、on_timer；写成数组或逗号分隔都认。
entry可选。入口类的类名；不写就自动找，实现 Skill 的那个类优先。
airun可选。工具的说明书：description（给模型看的说明）、returns（返回什么）、examples（用法示例）、params（参数表：类型、说明、是否必填、示例）。这一段写得越具体，模型填参越准。

扩展点不用在 md 里声明：只有 hooks 要写出来，因为钩子名本身不带类型信息；其余扩展点靠"这个类实现了哪个接口"自动认出来。所以一个技能可以同时是工具与上下文提供者 —— 写成两个类、放进同一个目录就好，不必挤在一个类里。

扩展点一览：每个管一件事

扩展点管什么
Skill提供工具：实现 call(Args, Host) 就是一把工具，md 里写了 tool: 才会注册给模型。装载期还能用 declare(Libs) 声明自己的库与表。
Hooked收事件：on_message 入站消息、on_timer 心跳、on_notice 通知（戳一戳、撤回、进群这类）、on_request 好友申请与群邀请。通知那条路只留痕，不发言、也不起一轮。
OutboundStage出站改文：发送前逐条看，可以改写正文、追加一条独立消息、一票否决；另有 finish 在整批收尾时拿到最终消息表，适合"@ 挂在首条""整批去重"这种要看到全局的事。
ContextProvider每轮往上下文里加一段：stable() 把它分成稳定段与易变段 —— 稳定段排在事实块之前，内容每次都一样就能吃到前缀缓存；易变段排在事实块之后。
LifecycleHook回合的开始、结束与即将发送这几个时刻，用来记账与清理（写历史、清临时态、私聊的"正在输入"）。它拿到的是只读口，改正文是出站那一段的事。
TriggerVoter决定这条消息要不要起一轮：ANSWER 回、DECLINE 不回（省掉一次模型调用）、ABSTAIN 交给下一个投票者，都不管就回到基板的地址规则。

这些扩展点的每一次调用都有独立超时，抛出的异常只丢它自己那一次，别的扩展点与这一条消息都不受影响；诊断信息以 [ext] 开头出现在日志里。

每个接口要实现的全部方法、护栏的细节与能直接落地的骨架，见下一节的 扩展点接口手册。

最小可运行示例：hello

先写 data\skills\hello\hello.md：

textdata\skills\hello\hello.md
---
name: hello
description: 打个招呼：把传进来的名字拼成一句问候
tool: hello
airun:
  description: 向某个人问好，回一句问候语
  returns: 一句问候话
  examples:
    - 「跟小明打个招呼」→ hello(who="小明")
  params:
    who:
      type: string
      description: 要问候的人
      required: true
      example: 小明
---

# hello

把参数里的名字拼成一句问候返回去。就这样，没有别的。

再写 data\skills\hello\Hello.java：

javadata\skills\hello\Hello.java
import sair.v4.skill.Args;
import sair.v4.skill.Host;
import sair.v4.skill.Skill;

/** 最小技能：一把工具，读一个参数，回一句人话。 */
public class Hello implements Skill {

    @Override
    public Object call(Args a, Host h) {
        String who = a.str("who", "").trim();
        if (who.isEmpty()) return "缺一个名字：参数 who 是空的";
        return "你好，" + who + "！好久不见。";
    }
}

就这样两件事。Skill 是唯一必要的接口，call 的返回值可以是字符串、对象、列表，也可以是空 —— 空就表示这次没话要说。

它怎么被模型看见：装载完成之后，工具面里就多了一把叫 hello 的工具。每轮的事实块里有一行能力索引，形状是"类别 → 工具 + 一句话"，模型就是从那里知道有这么一件事可以做的；ai/tools 也能看到当前工具表。参数表来自 airun.params，所以 md 里的说明写得具体一点，模型填参就准一点。如果 tool: 写的是中文或别的不合规范的名字，基板会自动转成一个可读的英文注册名，并在日志与清单里注明原来的写法 —— 不用自己纠结命名规则，但用英文会更好认。

怎么装载与生效

  • 把目录放进 data\skills\，启动装配的「技能扫描」那一步会扫一遍并编译它，日志里出现 [skills] hello → LOADED 工具=hello 这样一行。
  • 改了 .java，或者改了 md 的 front matter（tool / hooks / entry / airun）：敲 ai/skill reload 重新扫一遍就好；顺手敲 ai/restart 也可以，代价是基板要重装一次。
  • 只改了 prompt.md：不用 reload，保存之后下一轮读到的就是新文案（按文件的修改时间失效）。
  • 把整个目录删掉再 ai/skill reload，它的工具与钩子会一起摘掉，回到没有它的样子。

碰资源之前，先问一句位

技能要碰基板的资源时，先向宿主问一句"这一位我有没有"。放行时返回空，被拒时返回的是一句可以直接回给模型的人话；我们照实把它回出去就好，不用绕路，也不用另编一句。缺位本身就是答案。

要碰什么怎么问
读一个库h.needDb("memory", 'R')
写一个库h.needDb("memory", 'W')
读文件或目录h.needPath(路径, 'R')
写文件或目录h.needPath(路径, 'W')
平台动作（发消息、禁言、改名片这些）h.needPlatform("send_group_msg")，一律问 X 位
她自己的自主行为（定时、收表情、维护）h.selfDb(...) / h.selfPath(...) / h.selfAct(...)，判定主体固定是她自己，与"谁在说话"解耦

工具入口本身也是一道门：工具属于 T 类，判定的是 tool: 那一条的 X 位。普通用户默认没有这一位，所以对他来说这把工具在工具面里根本不存在 —— 看不见，也就调不动。想让某个人用上，是在 perms.json 里给他开一条例外，而不是在技能里自己判断"这个人能不能"。

她自己也能写技能

技能库那把工具（skill_write）平时由主人用，她自己也可以走同一条路：先用 op=draft 把 md 与 .java 落进草稿区（默认 data\skills-draft\）—— 草稿不参与扫描、不进工具表，写到一半不影响在跑的东西；确认之后再 op=promote 搬进技能库，搬完当场重扫一次；想手动再扫一遍，op=reload 也可以。

人也可以走同一条路（draft → promote），或者更直接一点：自己把目录放进 data\skills\，再 ai/skill reload。两条路的结果是一样的 —— 技能库里那个目录就是全部真相。

四条顺手就能避开的经验

热重载换的是新类加载器

每次重扫都会用新的类加载器重新定义你的类，上一份的静态字段不会跟过来。所以状态放在 kv 或自己的库里，别放在 static 上 —— 不然重载一次就像换了个新人。

周期的事交给心跳

需要定期做的事挂在 on_timer 上就好，它跟着基板唯一那条心跳走；自己起线程容易在关停之后还留着，也会让"到底什么时候跑"变得不好追。

异常在技能里收口

一条消息不该因为技能里的一次意外就整条垮掉。把异常就地收成一句可读的说明返回；钩子那条路是入站的同步路径，尤其值得这样做。

面向用户的话留在 prompt.md

话术、阈值、示例这些放进 prompt.md，改文案就不用重新编译；写在 Java 里的话，下一次改一句话都得走一遍 reload。

扩展点接口手册

上一节讲的是"一个目录怎么变成技能"。这一节把六个扩展点的接口逐个摊开：什么时候轮到你、要实现哪几个方法、签名照源码抄、哪些东西能动哪些不该动、在 md 里怎么声明。每个接口后面都跟一段能直接落地的骨架。

接口一 · Skill：给模型的一把工具

什么时候被触发：模型在对话里决定用这把工具的时候。它出现在每轮的能力索引里，模型把参数填好调一次，返回值回到对话里接着往下走。不写 tool: 的技能不进工具表，模型那边看不到它。

要实现的方法：

javasair.v4.skill.Skill
Object call(Args a, Host h);          // 唯一一个抽象方法，实现它就成了工具入口
default void declare(Libs libs) { }   // 可选：装载期声明自己的库与表

返回值可以是 String / Map / JsonObject / List / null，null 就是"这次没话要说"。参数用 Args 强类型取：a.str(k, def)、a.l(k, def)、a.i(k, def)、a.b(k, def)、a.obj(k)、a.arr(k)、a.strs(k)；参数缺了，回一句 a.missing(k) 是常见的做法。

能改什么、不能改什么：能借 Host 那一面调度基板已有的资源（六库与 kv、模型、NapCat、提示词、上下文注入、派子 Agent、说话、控制台、调别的工具），改不动基板的骨架与判定。工具本身是 T 类资源，判定看 tool: 那一条的 X 位；碰别的东西之前先问一句位 —— h.needDb(库, 'R' / 'W')、h.needPath(路径, 'R' / 'W')、h.needPlatform("动作")，放行返回空，被拒返回一句可以直接回给模型的话。她自己的自主动作走 h.selfDb / h.selfPath / h.selfAct 这一组入口，判定主体固定是她自己，与"谁在说话"解耦。

最少几行的骨架：

javadata\skills\hello\Hello.java
import sair.v4.skill.Args;
import sair.v4.skill.Host;
import sair.v4.skill.Skill;

public class Hello implements Skill {

    @Override
    public Object call(Args a, Host h) {
        String who = a.str("who", "").trim();
        if (who.isEmpty()) return a.missing("who");
        return "你好，" + who + "。";
    }
}

在 md 里怎么声明：写 tool:，再给一段 airun 说明书。参数表写得具体一点，模型填参就准一点：

textdata\skills\hello\hello.md
---
name: hello
description: 打个招呼：把传进来的名字拼成一句问候
tool: hello
airun:
  description: 向某个人问好，回一句问候语
  returns: 一句问候话
  examples:
    - 「跟小明打个招呼」→ hello(who="小明")
  params:
    who:
      type: string
      description: 要问候的人
      required: true
      example: 小明
---

md 的文件名与目录同名。entry: 不写的时候，实现了 Skill 的类优先被挑中，所以只有一把工具的技能不必写它。

接口二 · Hooked：挂在事件上的那只手

什么时候被触发：基板收到事件之后、往下走之前。钩子是同步跑完的 —— 基板要看它有没有把这条消息接管掉，所以这一趟不适合做慢活。

要实现的方法：

javasair.v4.skill.Hooked
void on(String hook, JsonObject payload, Host h);   // 一个方法收全部事件

hook 是事件名，四个都在 hooks: 里写：

钩子名什么时候来payload 的形状
on_message一条入站 QQ 消息到达，网关处理这条消息的当下NapCat 消息事件 JSON，基板再加上调用者视图与接管标记
on_timer基板唯一那条心跳，周期见 tickMs{"tick":n,"ts":毫秒}，只有这两个键
on_request一条好友申请或群邀请到达NapCat 请求事件 JSON
on_notice一条通知：戳一戳、撤回、进群、禁言这类NapCat 通知事件 JSON；这条路上只留痕，不发言、也起不了一轮

payload 从哪来：它就是 NapCat 推上来的那份事件 JSON，原样带下来，几个常见的键是 post_type（事件种类）、message_type（group / private）、self_id、user_id、group_id、message_id、raw_message、sender；消息钩子上基板还会补一个 _caller（调用者视图）与一个 _handled（默认 false）。

texton_message 的 payload（示意）
{
  "post_type": "message",        事件种类：message / notice / request
  "message_type": "group",       群消息还是私聊
  "self_id": 10001,              机器人自己
  "user_id": 20002,              这条是谁发的
  "group_id": 30003,             群号（私聊没有这一项）
  "message_id": 456,             这条消息的号
  "raw_message": "……",           原始文本 / CQ 串
  "sender": { "nickname": "……" },  发送者资料
  "_caller": { "……" },           基板补的调用者视图
  "_handled": false              置 true = 这条我接管了
}

读它用 Ev.parse(payload) 顺手一些：e.userId()、e.groupId()、e.messageId()、e.plainText()、e.rawMessage()、e.noticeType()、e.requestType()，判群私聊用 e.isGroup()。

判定主体是 SYSTEM：钩子里的动作属于"她自己的自动策略" —— 自动禁言、自动审批、自动清理都是这个口径。所以钩子能直接写库（C 类是 RWX），碰库之前用 h.selfDb(库, 'W') 问一句位就好；同时 h.caller() 仍然是那个真实发消息的人，两件事不要混：前者是"用谁的位判"，后者是"谁在说话"。定时那条钩子没有触发者，主体也还是她自己，所以 h.spawnAs(创建者, …) 这类入口在定时任务里格外顺手 —— 到点才跑的活按任务创建者的位判，而不是借走她的位。

能改什么、不能改什么：on_message 这一趟可以把 payload.addProperty("_handled", true) 置上，意思是"这条我接管了"，基板就不再自己回一轮（触发词接话走的就是这条路）。on_notice 那条路不读这个标记，也不读任何投票，是只读留痕的一条路。四条路都不改基板的消息内容 —— 要动正文，那条路是 OutboundStage。

接口三 · OutboundStage：出站管线的五道口

什么时候被触发：位置是分段之后、发送之前。所以它看的是逐条的消息 —— "这一条发不发、长什么样"，而不是"整条回复"。零 stage 时这条管线不存在，行为与没有这一层时一模一样。

要实现的方法：

javasair.v4.ext.OutboundStage
int order();                                                  // 唯一一个抽象方法，小的在前，同序按插件名
default String transform(Outbound m) { return null; }          // 改正文
default List<String> extra(Outbound m) { return Collections.emptyList(); }   // 追加独立消息
default boolean veto(Outbound m) { return false; }            // 一票否决
default List<String> finish(List<String> parts, Outbound m) { return null; } // 整批收尾

五个口的分工：

口拿到什么返回值的意思
order()不看内容小的先跑；同序按插件名。这个值在注册时取一次，所以排序不会随后续状态抖动。
veto(m)这一条当前的正文true = 这一条整条丢掉——否决是整条丢，不做"改一点点再发"。每条消息先问完所有 stage 的 veto，再进下一道口。
transform(m)这一条当前的正文null = 不改（"没意见"的默认）；改成空串或全空白 = 这一条被丢掉，后面的 stage 也不再处理它。
extra(m)整批的上下文（这时 index 指向本批最后一条）返回要追加的独立消息（比如"再追一张表情包"），空表 = 不追加。只在"确实还有话要发"的时候收一次，而且追加的消息不再过 stage。
finish(parts, m)最终消息表 parts（已含追加的那几条，元素已 trim），这时 m.total() 就是最终条数null = 不改；返回一张新表 = 整批换掉；返回空表 = 这一批一条都不发。表里的元素按原样发，不再过 stage。

为什么要有 finish：有的事天然是"整条回复"级别的，逐条口做不对 —— 典型是"@ 提问者加在首条"。"首条"得是真正会发出去的那一条，而在逐条口里看不到后面哪条会被别的 stage 丢掉或洗空，"@ 挂到一条根本没发的消息上"就是这么来的。它跑在 extra 之后，所以追加的表情包也算在 parts 里。extra 与 finish 返回的消息都不再过 stage，这一条防的是插件互相追加、无限繁殖。

手里的 Outbound 是什么：这一个对象在整趟出站里是逐条复用的同一个实例 —— 前一个 stage 的 transform 结果，就是后一个 stage 看到的 m.text()。它给的口有：text() / text(String)（这一条当前的正文，正式的改法是 transform 的返回值）、session() / group() / target() / caller() / echo()（落点信息，只读 —— 改"发给谁"不是扩展点的事）、index() / total() / first() / last()（这一条在本次发送里的位置）。caller() 在定时任务的落点上是 null，写插件时顺手担待一下。

出站这条路上没有回合，也就没有 BuildContext，所以文案与阈值从 m.host() 读自己目录的 prompt.md；m.host() 可能为 null，那时用兜底默认值就好。

接口四 · ContextProvider：每轮往上下文里加一段

什么时候被触发：每一轮装配上下文的时候。基板自己不产生任何一条上下文内容，它只负责三件事 —— 顺序、段位、预算，剩下的内容全在插件里。

要实现的方法：

javasair.v4.ext.ContextProvider
boolean stable();                                            // 稳定段还是易变段
int order();                                                 // 拼装顺序，小的在前
default int maxChars() { return 1200; }                      // 这一段最多多少字符
default boolean appliesTo(BuildContext b) { return true; }   // 只对哪些会话生效
String build(BuildContext b);                                // 产出这一段

稳定段与易变段：stable() 返回 true 的块排在同一条系统提示词之后、事实块之前，它们一起构成可以复用的前缀 —— 模型服务的前缀缓存是按前缀逐字节命中的，所以这一段的内容在同样输入下要逐字一致：时间戳、随机数、当前消息正文放进去了，缓存就从那里断开。返回 false 的块排在事实块之后，每轮都可以不一样；两边的顺序都还是按 order、插件名定，同输入逐字节可复现。

哪一段该稳定，一句话的判据：内容只取决于"这个插件自己的配置"，就放稳定段；内容取决于"这一轮谁在说、说了什么、现在几点"，就放易变段。拿不准的时候放易变段更稳 —— 它不影响正确性，只是少吃一点缓存。

预算怎么裁：

  • 先按这一段自己的 maxChars() 逐段截断，丢的是尾巴 —— 开头的信息量最大。出厂默认 1200。
  • 再按全局 ctxBudgetChars（默认 6000）算总长；超了就从 order 最大的开始整段丢，并记一行 [ext] budget over。半截上下文比没有更坏，所以这里不截一半。
  • maxChars() 返回 <=0 = 这一段不按自身预算截断，但仍然受全局预算管 —— 它不是"要多少给多少"的开关。一个 provider 把整库拉进上下文，挨罚的是同一轮的所有人。
  • build() 返回空串或 null = 这一段这一轮不出现，这是正常结果，不算错。
  • appliesTo() 返回 false = 这一段这一轮不出现，基板也不会记成异常。基板不按调用者权限裁定扩展点行为（否则"给某人写画像"会随权限随机失效），这里是插件自己的策略口。

能改什么、不能改什么：这一段能决定"进去的是什么" —— 也就是 build() 的返回值，它会被 trim 之后按"一段一条 system 消息"装配。装配骨架、消息数、顺序、预算都不在插件手里：BuildContext 只给只读查询口，没有消息数组，也没有回合对象。要写东西就写自己的库、自己的 kv。

BuildContext 给的口：caller()（调用者）、session()（console / qq:123 / group:456）、text()（本轮正文：装配期是用户输入，出站期是将要发出去的正文）、host()（只读能力面，可能为 null）、group() / groupId() / qq() / master() / console()（从调用者派生的判断）、state(key, def)（按 key 读本轮事实，现有的键是 media / chat_window / subagent）、subagent() 与 agentLabel()（这一轮是不是子 Agent 在跑，是的话"有副作用的写"更适合改成"提议"）。

接口五 · LifecycleHook：回合的开始与结束

什么时候被触发：一圈回合的几个时刻，顺序是基板保证的：

text时序
onTurnStart → 模型跑（可能多次工具闭环）→ onSend（真要说话了）→ 落点发出 → onTurnEnd

装配完这一轮、还没跑的时候是 onTurnStart，那时"本轮输入、本轮事实"才齐；onSend 是"这一轮马上要对外说一句话了"，含失败兜底那句；正文发出（或失败）之后是 onTurnEnd，失败时 reply 是空串、error 非空，两种结果都会通知一次。它只管主回合 —— 子 Agent 与后台收尾回合不经过这里，因为它们是对外不可见、也不进对话历史的那些回合。

要实现的方法：

javasair.v4.ext.LifecycleHook
int order();                                              // 小的在前，同序按插件名
default void onTurnStart(BuildContext b) { }               // 回合开始（装配完、还没跑）
default void onTurnEnd(BuildContext b, String reply, String error) { }   // 回合结束
default void onSend(BuildContext b) { }                    // 即将把正文交给落点

能改什么、不能改什么：这一层的用途是记账与清理 —— 写对话历史、记调用量、清临时态、私聊的 typing。它拿到的是只读的 BuildContext，没有可改的正文，改正文是出站那一段的事。onTurnEnd 里拿到的 reply 是这一轮的产出，可能还没剥标记、也可能还没发出去，适合读、不适合改。

接口六 · TriggerVoter：这条消息要不要起一轮

什么时候被触发：一条入站消息到达、钩子那一趟跑完之后。基板要决定"这条要不要自动回"，就问一圈投票人。DECLINE 那一票能省掉一整轮模型调用，所以这条路值得就地判断。

要实现的方法：

javasair.v4.ext.TriggerVoter
enum Vote { ANSWER, DECLINE, ABSTAIN }

int order();                                   // 小的在前，同序按插件名
Vote vote(Ev ev, Caller c);                    // 投票；返回 null 等同于 ABSTAIN
default String reason() { return "plugin"; }   // 拒绝的缘由，只在 DECLINE 时有意义

三态：

票意思
ANSWER回。即使没被 @、也不是主人（触发词命中走的就是这个意思）。
DECLINE不回，直接结束，省掉一整轮模型调用。
ABSTAIN不管，交给下一个 voter；全都不管就按基板原来的地址规则走。

判定口径：按 order、插件名依次问，第一个非 ABSTAIN 的票生效，后面的不再问 —— 顺序确定，结果才确定，这也是它不做成"多数决"的原因。抛异常或超时 = 这一票作废当 ABSTAIN，记一行 [ext]。这条路在消息到达的当场跑，超时上限是 extTimeoutMs（默认 200 毫秒），所以宁可 ABSTAIN，也不在这里等网络。被拒时 reason() 那句话会写进 [qq] skip reason=… 的结构事实里，起个看得懂的名字，事后好查。

六个接口共有的护栏

这些约定对上面每一个接口都成立，写插件时按同一套习惯来就好：

每次调用都有独立超时

配置 extTimeoutMs，默认 200 毫秒。超了这一条就当它这次没说话：上下文这一段不出现、出站这一口不改、这一票作废、这一次回调跳过 —— 别的扩展点与这一轮本身都照常。

抛出的异常只丢它自己

一次意外只让它那一次调用失效，正文保持进来时的样子，日志里多一行 [ext] error。基板的承诺是"永不失联"：外挂可以慢、可以崩、可以一次吐很多字，那一轮都照常跑完、照常回话。

手里的对象是"这一次的视图"

BuildContext 与 Outbound 过了这一次就作废，把它们存进字段，下次读到的就不是这一轮的东西了。要留状态留在自己的库或 kv 里。host() 还可能为 null，拿不到就少做点事。

热重载换的是新类加载器

每次重扫都会用新的类加载器重新定义你的类，上一份的 static 字段不会跟过来。状态别放在 static 上 —— 不然重载一次就像换了个新人。

两条不显眼但常打交道的约定：一个是同一个插件的扩展点调用是串行的（基板按实例加锁），所以同一个插件的两轮不会同时进它的扩展点，插件作者不用自己处理并发；另一个是扩展点在基板自己的扩展工作线程上跑，不占回合线程 —— 超时因此才有意义。诊断都带 [ext] 前缀：每个扩展点一行 [ext] 事情=插件名:类名 chars=… ms=…；status.ext 还能看到逐条的调用次数、出错与超时次数、贡献字符与总耗时。总开关是配置 extEnabled（默认开），关掉就退回"零外挂"行为；一条扩展点都没挂的时候，四个接线点一行代码都不多走。

一个完整的组合例子

一个类可以同时实现多个接口 —— 基板装载时会扫这个目录编译出的每个顶层类，按"它实现了哪个接口"逐条挂上去，ContextProvider / OutboundStage / TriggerVoter / LifecycleHook 这四个各算一条。下面这个技能只写了一个类：既收 on_message 记账，又每轮注入一段。

textdata\skills\群账本\群账本.md
---
name: 群账本
description: 收群消息记一笔流水，并把最近一条注入上下文
hooks: on_message
entry: GroupLedger
---
javadata\skills\群账本\GroupLedger.java
import com.google.gson.JsonObject;

import sair.v4.ext.BuildContext;
import sair.v4.ext.ContextProvider;
import sair.v4.qq.Ev;
import sair.v4.skill.Host;
import sair.v4.skill.Hooked;

/** 一个类同时挂两个身份：收消息记账 + 每轮注入一段。 */
public class GroupLedger implements Hooked, ContextProvider {

    // ---------------- Hooked：一条入站消息记一笔 ----------------

    @Override
    public void on(String hook, JsonObject payload, Host h) {
        if (!"on_message".equals(hook) || payload == null || h == null) return;
        try {
            Ev e = Ev.parse(payload);
            if (e == null || !e.isGroup() || e.groupId() <= 0L) return;
            h.store().kvSet("ledger:last:" + e.groupId(), e.userId() + "：" + e.plainText());
        } catch (Throwable t) {
            // 记不上就少一条，消息照常
        }
    }

    // ---------------- ContextProvider：每轮注入一段 ----------------

    @Override
    public boolean stable() {
        return false;                        // 每轮都可能变，放易变段
    }

    @Override
    public int order() {
        return 45;
    }

    @Override
    public int maxChars() {
        return 400;
    }

    @Override
    public boolean appliesTo(BuildContext b) {
        return b != null && b.group();
    }

    @Override
    public String build(BuildContext b) {
        try {
            Host h = b.host();
            if (h == null) return "";
            String last = h.store().kv("ledger:last:" + b.groupId(), "");
            return last.isEmpty() ? "" : "【本群最近一条】" + last;
        } catch (Throwable t) {
            return "";
        }

运行期：分道调度 + 回合 + 心跳

每会话一条道

同会话严格先进先出、同一条道同时只有一个在跑；不同会话互不相干 —— 一个慢群不再堵住别人。真正并行的是工作线程（turnWorkers，出厂 2）schedule\Lanes.java。

溢出不静默

默认把后到的消息并进该会话还在排队的那一条（合并不新增待办）；装不下或选了丢弃策略时回一句可读文案，绝不静默消失。另有两道硬上限保证内存有界 Lanes.java。

优先级与老化

出厂口径是主人/私聊优先于群；道首任务带入队时刻，优先级老化保证普通道不会被高优流量饿死 Lanes.java。

唯一的心跳

全基板只有一条周期 tick，做两件事：派发周期回调；检查到点的定时唤醒任务，到点就唤起主 Agent 跑一轮并把结果送回目标会话 Tick.java。周期出厂 20000 ms，下限夹到 1000 ms Tick.java、Conf.java。维护与出站台账裁剪也在心跳里 store\Store.java。

模型调用闸门

主回合、定时任务、异步子 Agent 都要过同一个闸门：许可数出厂 1（不并发），等待上限 180 s，等不到就放弃本次调用并收敛成一条失败结果 Boot.java、DeepSeek.java、Conf.java。

回合与收尾

一次回合跑到"模型不再要求调工具"为止；后台完成的任务回灌后触发一轮收尾回合，那一轮只记账不对外说话 agent\Loop.java。

关停：ai/exit 只停基板

先知道这一条实现行为：ai/exit 会停基板 + 收掉两个调试口 + 关落盘句柄 + 注销控制台捕获器，但不结束进程（V4Activity.java、dev\DebugShell.java、dev\DebugPort.java）。后果：基板停下后调试口就关了，而进程仍然活着；此时若没有可用的控制台，就没有任何入口再敲一次 ai/start，基板起不回来。这是当前实现行为，未计划修改：把壳卸载当成调试面的终点是有意为之（在同一个壳里 ai/start 与 ai/restart 收的只是基板，观测面照旧）。

正确关停一：/exit

要走框架自己的关停路径，用控制台的 /exit（调试口那条"关框架"的命令走的就是它）。组件 ai/exit 的语义是"停基板、不改配置、不卸载插件、之后可再 start" term\Cmd.java —— 只有在确实还有控制台可用时它才是可逆的。

正确关停二：按精确 pid 结束进程

没有控制台、也不打算再让它工作时，可以直接结束那个确切的 pid（部署口径见 02 · 部署）。按名字批量结束这类粗口径容易误伤 —— 一台机器上可能同时跑着别的实例。

重装 vs 重启：ai/start 幂等，已就绪时只回"已在运行"，绝不重启；要按新配置重装只有 ai/restart。装配/重启同时只允许一条，重复命令会被明确拒绝 V4Activity.java。

04 / MODEL

六件事

非流式对话

流式输出

账户余额

模型清单

字段语义
self这一轮真正在跑的模型。缺键时回落到配置里的主模型；子 Agent 带了自己的模型时，该键写在事实块装配之前，所以子 Agent 看到的是它自己
self_has_vision这个模型自己能不能看图（按配置的追加项判定的白名单真值）。不因识图档位为 no 而改写成 false —— 那是把事实编掉
main配置里的主模型名（与"这一轮跑谁"无关；主回合下两者相同）
main_has_vision主模型自己能不能看图
vision配置里指定的具备视觉能力的模型名（需要看图时可以派一个用它的子 Agent 兜底）

recognizer识图组件注册的那个约定工具名在不在工具面。不在面时照实答 off；每次现问一遍工具面（热重载后立刻变对），绝不抛：探测口出岔子 = 当作不在面

"我能不能"与"允不允许"是两件事：self_has_vision 说的是能力，mode 说的是这一轮允不允许挂图。把 mode 设成 off 不等于她失去看图能力 CtxBuild.java。

图片是怎么"挂"上去的

挂图判定是一个纯函数（无模型、无网络、无时钟、不读配置、不读库、不改入参），唯一入口是三档判据的扫描函数（src\sair\v4\qq\MediaAttach.java）：

① 段型

得是图片段（大小写不敏感）；表情类段不认 —— 它们没有 URL。

② URL 可用

得是 http:// / https:// / data:image/，与入站侧逐字同一口径；那一处是私有方法，所以这里复制口径，并在注释里写明这是唯一需要人工同步的地方。

③ 张数与体积

图片序号得 ≤ 上限（出厂 4；≤0 = 一张都不挂）；体积字段缺失就放行，存在则要 ≤ 上限（出厂 4 MiB）Conf.java。

降级要看得见：丢掉的每一张都带序号与原因（超张数 / 超体积 / URL 不可用）；一张都没挂上时产出一行状态事实，原因取值覆盖"识图关了""这一轮走 relay""挂图关了""全被丢"。绝不静默 —— 她要是不知道图没挂上来，就会凭空描述图里有什么（MediaAttach.java）。挂上之后追加一句"图已在本轮第 1 次请求里看过，后续请求只有文字" MediaAttach.java。

模型面的边界

没有自动路由

model=auto 就是取自动档模型名（出厂 deepseek-flash），不做任何路由判断；"实际调用用的模型"只有一个函数决定 Conf.java。换模型只有三条路：改配置、子 Agent 指定、单轮覆盖。也不新增配置键 RecognizerState.java。

"看图"不自动发生

图片段在事实里原本只是一行给机器看的 JSON；要真的看图得靠 mode=native 时把 URL 挂进请求体，或派一个会看图的子 Agent 兜底 MediaAttach.java、CtxBuild.java。

通知也留痕

通知事件被翻成一行确定性标签（例如"撤回"那类会带上操作者、群号与消息 id），与消息同表：群通知落群聊历史、私聊通知落对话历史。认不出的通知类型也给一行带类型与子类型的标签，绝不静默丢弃；撤回事件自成一行，不去改那条被撤回的原行（qq\NoticeRender.java；QqGateway.java）。

本地文件外链中转（跨机部署）

部署事实是：NapCat 与插件不一定在同一台机器，而上传动作的文件参数如果是本地路径，只有同机的 NapCat 读得到。所以"把本地文件变成 URL"被算作连接 NapCat 这件事的一部分，不是业务能力（src\sair\v4\qq\Relay.java）。

开启条件

开关出厂 false 时启动直接返回失败，端口不监听 Relay.java；端口出厂 2671 Conf.java。开了之后，本地文件在唯一出口那里被统一换成外链 URL。

三道闸

① 默认关闭；② URL 形如 http://主机:端口/<凭据>/<绝对路径>，凭据不对一律 404（不区分 401/403，避免探测），凭据可在配置里复现、手改；③ 只读：只接受 GET / HEAD，别的方法 405，没有目录列举、没有写入、没有删除 Relay.java。

风险口径（明确取舍）

服务拥有完整文件访问权：任意本地绝对路径都能中转，不做目录白名单 —— 因为发送能力本身就要能从任意路径发文件。能拿到链接 = 能读那台机器上的文件。所以只有"NapCat 确实在别的机器上"时才开，并建议配上有效期让它到点自己关掉 Relay.java。日志脱敏：凭据只打前 4 位 Relay.java。

没开中转时：本地绝对路径回退成同机的文件 URI（与既有现场验证一致），图片与语音段原样透传 —— 这两类段本来就认同机本地路径 Api.java。中转起不来只记一行、不影响别的能力 Relay.java、Boot.java。

为什么消息流留在基板：对话历史与群聊历史这两张是环境：基板是它们唯一的写入者，也是上下文装配的读者。交给外挂单元声明会出现"单元不在 ⇒ 基板自己的上下文没有历史" EnvLibs.java。

中文全文检索：三元组分词 + 三层回退

有全文索引的库走索引匹配（中文靠三元组分词器），无索引或索引无果时回退子串匹配，结果行带命中来源说明（store\Store.java）。建索引时先试三元组分词器、失败才退回默认分词器；每个索引表挂三个同步触发器（插入后、删除后、更新后），并立刻做一次重建 Db.java。

为什么要"拆词并联"这一层

把整串包成一个索引短语，对单个词没问题，但对多词、带空格的自然语言查询几乎必然零命中 —— 短语要求这些词在原文里连续且同序。所以检索是三层：短语 → 拆词并联 → 子串匹配 store\FtsQuery.java。

切词口径

先洗掉链接、CQ 码与图片标记（否则链接里的片段会被切成三元组、产生数万条无关命中）；中文取三字滑窗，英数词保留整词（≥4 字符，或含数字的 3 字符）；分词器要求查询项 ≥3 字符，所以 2 字中文词只能交给子串匹配 FtsQuery.java。查询项上限 8（过多会稀释排序权重），超了均匀采样 FtsQuery.java。

拆词只对中文启用：纯 ASCII 查询不启用这一层 —— 子串匹配本来就是对的口径，而拆词会把通用英文片段召回一堆无关记录。判据就是"查询里有没有中文" FtsQuery.java。

索引也可以按库关掉：配置里列出的库连索引带触发器都不建，检索只剩子串回退 —— 用检索速度换文件体积 Db.java。另外"删索引"是唯一能真把索引占的空间还回去的动作，且空间要等一次整理之后才真正还给文件系统 Store.java。

保留期清理口径

动作口径旋钮与出厂值
删超龄低重要度记忆时间早于"现在减保留天数"且重要度 ≤ 4（低重要度的界定是常量，不是配置）保留天数，未给时 30 天
低重要度截断只保留最新 N 条；≤0 = 不截断截断条数
清超龄对话历史删更早的对话行；≤0 = 不清理（0 偏向不删，不是"用默认值"）对话保留天数
清超龄群聊历史删更早的群聊行；≤0 = 不清理群聊保留天数
裁剪出站台账只按"最近 N 行"裁，不按时间（撤回通常发生在近几天内）；每次维护裁一次固定 2000 行

两条容易踩的边界：① 笔记性质的库不受维护影响（从不删）Store.java；② 展开类缓存的有效期会被夹到"群聊保留天数 × 24" —— 维护完全不清键值表，不夹这一刀，别人的话会活得比群聊记录还久 Conf.java。

库门面还提供什么

统计与导入导出

统计给出库文件、含预写日志的占用、各库条数、总条数、索引是否可用；导出为一行一条 JSON 的文本文件，导入逐行插入并回报行数 Store.java。

出站消息台账

她每发出一条消息，就把拿到的消息 id 记进账本 —— 撤回只能按它定位，而这个 id 以前是用完就丢的。记账是"发后即忘"的：它不可能改变、吞掉或拖住动作本身的返回值 qq\Api.java。

补列幂等且安静

老库补列先查表结构、缺了才加。SQLite 没有"加列 if not exists"，直接写会让每次启动都刷一条吓人的假报错 store\Lib.java。

08 / PROMPT

提示词面：一份自带 + 一个注入台

基板只带一份初始提示词，且自己不写死任何正文 —— 文件不存在就是空提示词，不报警、不兜底。

自带的三份实体文件

这三份分别是 prompts\identity.md（初始提示词）、prompts\subagent.md（子 Agent 的公共段）、prompts\tools-index.md（工具索引）。初始提示词与子 Agent 公共段都可以在运行期重新读一遍 prompt\Prompts.java。子 Agent 的变化部分（角色、边界、输出格式）由主 Agent 在派发时生成，文件里只有公共段 Prompts.java。

注入台：四个槽位

槽位作用
系统槽追加进系统提示词（影响角色与规则）
上下文槽追加进每轮动态上下文（影响本轮事实）
工具槽补充工具描述（影响模型怎么用某个工具）
参数槽拼在用户消息之前（一次性的强提示）

全局作用域对所有会话生效；其余键是会话键（群、私聊、控制台三种），只对该会话生效。渲染时先全局后会话，同 key 会话覆盖全局；每个槽位最多保留 64 条，超出丢最旧 prompt\Inject.java。

硬边界：路径锁在提示词目录内：相对名会被解析成目录内的真实文件，越界（上跳、绝对路径、软链逃逸）或非 md 一律返回空。注释写明理由：曾经可以借"读某个名字"读到配置文件里的密钥 Prompts.java。

改文件不等于立即生效：配置类改动只有 ai/start 或 ai/restart 才被读进生效面；提示词正文有它自己的热重载，不受那条口径影响 term\Cmd.java。

09 / AGENT

Agent 面：主循环、子 Agent、连续失败闸门

一次回合跑到"模型不再要求调用工具"为止；工具表按调用者权限筛出来，可选再叠加一个白名单用来收窄子 Agent 的能力。

主循环

上下文每一轮都重新读系统提示词与上下文注入，因此运行期注入随时生效 agent\Loop.java。一轮的结果结构是显式的：正文、轮数、工具调用次数、耗时、错误 Loop.java。

机制口径
连续失败闸门同一个工具连续失败达到提示阈值时，下一轮往上下文加一行纯事实（工具名到次数的映射 + 最后一次错误）；达到终止阈值就停止本轮并回终止文案。判定只看结构信号（结果首行的前缀标记 + 自报的成败标记），没有关键词表、没有劝导语；阈值与终止文案都在 data\prompts\tools-index.md，缺键只报错、不兜底

单轮模型覆盖可以带自己的模型；这个覆盖同时决定"这一轮是谁"，与子 Agent 写的是同一个键同一个值，因此幂等

子 Agent

后台回合走同一条队列

后台回合排进"按会话分道 + 优先级"的同一套队列，避免与主回合并发打模型 Agent.java。

装配骨架

动态聊天窗口

每触发一次就现取

不再有游标、不再有"上次触发点到这次触发点"的增量、不再有落库的进度状态 —— 每一轮都重新取最近 N 条，大小只有一个旋钮，出厂 30 条，私聊与群一视同仁 ctx\ChatWindow.java；CtxBuild.java。

两个源，不对称

11 / TERM

控制台与界面

控制台既是输入面（命令表），也是可读信息源（流式捕获 + 游标读）。对话正文被单独承载到一块面板上，主输出框只留结构性日志。

命令表：永不失联

分层帮助

命令表按"对话 / 生命周期 / 基板状态 / 能力"分组自述，末尾写清两条口径：除 ai/start 与 ai/restart 外其余命令只改配置文件；业务能力不在控制台命令里 term\Cmd.java。

不炸框架

路由与帮助不向框架层抛异常：任何命令炸掉都收敛成一行可读失败 + 允许继续输入下一条 Cmd.java。

等待有上限

对话命令有三层前置判断（装配齐备 / 密钥 / 队列未满）+ 等待上限，绝不在队列堵死时把控制台永久卡住 Cmd.java。

控制台捕获：三层读法

框架自带的"取当前可见全文"有一个硬伤：一旦有人清屏、或控制台按内存预算裁掉最旧一半，那段输出就再也拿不回来；而且每轮把整段控制台塞进上下文既贵又重复。所以捕获器提供三层（term\ConsoleTap.java）：

层做什么上限 / 出处
流式捕获注册一个打印代理，每条输出（去色、带时间戳与来源线程）写进有界环形缓冲。缓冲在进程内独立于控制台文档，所以清屏之后仍读得到最近输出出厂 500 条 / 64 KB ConsoleTap.java
全量读取取当前可见全文（带长度上限与截断）。这是补充，不是主路径单次出厂 4000 字符 ConsoleTap.java
游标读取每条缓冲带自增序号，只回"比上次序号更大"的新增部分 —— 调用方记住游标即可，不会每轮重复吃同一段输出ConsoleTap.java

打印代理的硬约束：框架的实现是"只要注册了任意一个代理，框架自己就不再打印"，而是把输出交给每个代理、由代理负责真正写进控制台。所以捕获器要转发，不然控制台会被弄空。转发档位出厂是自动：只在自己是唯一代理时转发，若还挂着别的代理就只捕获、不重复打印，避免同一行出现两次 ConsoleTap.java。

无界面环境不报错：控制台窗体是类加载即建窗体的单例，无界面环境里它静态初始化会失败。捕获器所有入口都包在异常兜底里：装不上就标记未安装，读返回空、写返回一句可读原因，绝不把异常抛给基板 ConsoleTap.java。

输出分流

输出落点有四种，各自独立实现：静默、控制台、QQ（群与私聊）、定时任务（term\Sinks.java）。发送前还有两道：

出站改写管线

分段之后、发送之前跑一遍。注入口默认是空的 —— 没人注入过就等于零改写，行为与加这一层之前逐字节一致；改写层自己炸了这一条按原样发（"改不动的东西，不能因为它坏了就丢话"）Sinks.java。

出站最后一道闸

拦"正文里混进了模型的工具调用标记"这一种情况：判据是结构（标签形状 + 结构词），不是关键词表；命中就整条不发，绝不"正则删字符后照发"（半剥的残留比一条都不发更像乱码，还会把残缺内容写进聊天记忆）。要拦的那一条丢了，其余条照发 Sinks.java。

分段的段位口径：显式分段标记优先 → 按长度分段 → 群聊再压短一档；长度切点依次找换行、句末标点、次级标点，尽量不把句子劈成两半 qq\Seg.java。

本地对话面板

它解决什么

本地控制台就是主人对话。流式正文与结构性日志混在同一个输出流里，正文会被装配、工具、统计行冲散。面板把对话单独承载到一块面板上，再按框架现成的控件输出协议挂进控制台的选项卡隔离区，从而主输出框只留结构性日志 ui\TalkPanel.java。

怎么挂上去

公开入口只有"打印一个组件"这一个方法，它按类型分派：画布类会新开一个选项卡进隔离区；标题取组件自己的名字。隔离区是主窗口中心面板右侧的停靠区，与文本流完全隔离 —— 进选项卡的东西不写进主输出框 ui\TalkMount.java。

线程纪律（不是洁癖）

任一线程都可以追加内容，但它们只动账本；真正的文档写入由界面线程上的一次落盘统一做。理由写在注释里：富文本文档的插入会派发文档事件，其中"元素结构变化"是异步排进界面线程的，非界面线程写入会与正在跑的视图更新打架，会把界面线程打死 —— 窗口留着最后一帧、事件再也没人处理 TalkPanel.java。挂载动作也投递到界面线程上做 TalkMount.java。界面元素建不起来就退化为内存记录，绝不把异常抛给基板 TalkPanel.java。

AI 读控制台 / 跑框架命令（仅主人）

基板工具面里有一把控制台工具，说明第一句就写明是仅主人：支持读最近输出（游标式）、执行一条框架命令并回它打出来的新输出、看最近的框架命令、打印一行、清屏、看控制台规模 Builtins.java。

12 / DEBUG

调试面：四个东西，各自能做什么

控制台捕获、调试输出口、调试落盘、调试输入口。前三样是"看得见"，最后一样是"能伪造"—— 所以它的权限要求最硬。

东西能做什么起停 / 权限要求
控制台捕获 把控制台每一行收进有界环形缓冲（去色 + 时间戳 + 来源线程），支持流式、全量、游标三种读法 与壳同生共死（不是可开关的端口）；它的注册与注销也归壳层管
调试输出口 在进程外"看框架输出、像敲控制台一样下命令"。命令表：连通性探测、状态摘要、增量读控制台（游标式）、读最近 N 条、看框架命令历史、帮助、按框架那条路关框架、只关这条连接；其它任何一行都当框架控制台命令执行，回它的输出 端口固定 127.0.0.1:2660；只绑回环，外部网卡够不着；凭据必填，为空直接拒绝启动；只有 ai/debug on|off 能起停它
调试落盘 内存里的两路捕获都是有界环形缓冲，回答不了"从起实例到现在一共发生了什么"。落盘把每一行同时写进文件，于是"一次取全部输出"成为可能 落点在数据根下的日志目录，两个文件：控制台日志与对话日志；按天 + 按大小滚动（单片段超 8 MB 就改名封存，另开新的当天片段）；只增不删，要清理只能人工删
调试输入口 就两件事：① 以任意 QQ 身份（含主人）造一条入站消息（私聊或群聊，或原样的任意事件）—— 落点与真实帧走的同一个入口，去重、黑名单、路由、调度、回合、权限判定一样都不少；② 以框架控制台的身份下一条框架命令（与工具面那条命令是同一条路，没有第二条实现） 端口固定 127.0.0.1:2661；只绑回环；凭据必填且与输出口共用同一个；关掉仿真开关时端口照常监听、认证照常能过，但每个动作回"仿真已关"—— 绝不表现成"连不上"

凭据怎么给

不开裸口

两个口都不允许无凭据裸开：凭据为空就拒绝启动并打一行可读原因（两个口一起拒绝）。命令不带凭据时现场生成一个，写进运行现场凭据文件 dev\DebugPort.java。

凭据文件

运行现场凭据文件是唯一真源（名字、主机、端口、进程号、两个口共用的凭据与指纹、时间戳）。指纹用于诊断，绝不回显凭据本身 DebugPort.java。

不归配置管

本机调试口的四个键已整条撤出配置面：它们不再是配置文件里的键，起停只看 ai/debug on|off|status Conf.java、dev\DebugPort.java。

壳层与基板层的分界（这条容易搞错）

层管什么什么时候收
壳层绑定"当前基板在哪"这个稳定宿主引用 + 装调试落盘 + 控制台捕获的注销随壳存在而存在；只有壳卸载才收（停两个口 + 关落盘句柄 + 解绑宿主，且绝不删日志）
命令层只管两个端口off 只停端口，不停落盘、不删任何日志文件
基板层什么都不碰调试面停基板不等于停观测面

两个口"现取"活基板，绝不缓存：口是在 ai/debug on 时起的，而那条命令故意允许在 ai/start 之前敲（那时只有一个空壳）。真正的基板是 ai/start/ai/restart 时另建的一台。所以两个口每次要用基板都现问现取，ai/start 之前如实报"未启动"，而不是拿着过期的壳 dev\DebugPort.java、dev\DebugShell.java。

调试口自己的硬防护

单条长度

入站单行超过 8192 字符就断开，不让一行把内存撑爆 DebugPort.java。

连接数

并发连接上限 4，超了直接拒（回一行忙就关），不让连接堆积 DebugPort.java。

空闲超时

一条连接 120 秒内一个字节都没来就自己断，防止连接挂死 DebugPort.java。

认证比对

认证用常量时间比对；失败日志限流（同一来源 10 秒内最多一行），防重试把控制台刷爆 DebugPort.java。

调试口自身不会让基板起不来或停不下来：一条接受线程 + 每连接一条守护线程，全部包在异常兜底里 DebugPort.java。它下命令有执行上限（60 秒），等不到就回超时（命令本身可能还在界面上跑）DebugPort.java。

装配不再自动起调试口：装配最后一步只在日志里写一句"本机调试口未自动启动：要看调试面就敲 ai/debug on"，连"读配置试着起一次"都没有 src\sair\v4\Boot.java。也就是说端口什么时候开只有一个出处，也只有一条能关掉它的路。

13 / BOUNDS

边界与"不做什么"

能力清单的另一半是明确的"不"。下面每一条都有出处，也都可以反过来验：代码里找不到那个抽象，就是真的没有。

不做的十一件事

不做口径
没有"通道"这一层抽象会话键只有三种形状：群 / 私聊 / 控制台。入站按消息类型直接分流到群聊或对话两张表，没有"适配器 / 通道 / 平台"这些中间抽象，也没有可注册的第二种平台
不做模型自动路由model=auto 就是取自动档模型名，"实际调用用的模型"只有一个函数决定：无路由、无分类。视觉对话也走同一条链路
不做业务能力控制台命令表只保留"对基板操作"的命令；业务能力一律不在基板与控制台命令里
不做目录监听装载时机只剩"启动这一次扫描"与"显式重载"两种；曾经有过的"按修改时间轮询自动重扫"已整条删除
不识别媒体内容语音 / 视频 / 文件只出标签，不做识别；折叠转发只出标签，内容未展开（展开那几个键已登记但没人读）
默认拒绝三个身份里只有主人恒全权；普通用户对 A/B/E/T 一位都没有、对 C 只有读。位名认不出返回哨兵，判定链上拿到它就当"没有权限"。权限面没装配时，连接闸门按拒绝处理
不给运行表开后门好感度、定时表、子 Agent 台账、通用键值、单元索引、出站台账这六张运行表不进可查询库；把好感度做成"库"就等于让达标的人绕过授权动作直写自己的数值
不自动清日志调试落盘只增不删，连最旧的分片也只改名归档；长期运行日志目录会持续变大，清理是人工动作
不做静默失败队列溢出要回一句可读文案；合并装不下也要回；丢掉的图要带序号与原因；通知认不出也要留一行标签；黑名单读不出来按"没拉黑"处理（宁可多回一句，也不让消息静默消失）
不做"停基板 = 停观测面"停基板一个字节都不碰调试面；调试落盘随壳存在而存在，只有壳卸载才收，而且绝不删日志
不结束进程ai/exit 只停基板、不改配置、不卸载插件；它不结束进程，而壳卸载恰恰是调试面的终点 —— 所以无控制台场景下这条路不可逆，见 生命周期 · 关停

"计划中／未实现"清单

这些键现在写进配置也不会改变行为：折叠转发展开的四个键（开关、节点数上限、深度上限、字符上限）已在配置面登记，但当前没有任何代码读它们 Conf.java；同一批里只有引用展开总开关与缓存有效期被真正读取 Conf.java。所以"转发内容自动展开"这项能力计划中／未实现，现状是一行 [折叠转发 id=… 未展开] 标签 qq\MediaRender.java。

另外两条已知的能力边界：① 识图组件的计数是内存计数 —— 跨日归零、进程重启后从 0 重计、不落盘，别把它当持久账本用，也别拿它算"历史总量" ctx\RecognizerState.java；② 动态聊天窗口不报"还有多少条更早的"，因为那要额外一条统计查询 —— 她看到的是"窗口里有几行、多少字符" ctx\ChatWindow.java。

一条判据：找不到那个抽象，就是真的没有
