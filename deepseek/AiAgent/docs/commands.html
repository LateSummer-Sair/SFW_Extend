调用约定

一、通用调用约定

命令怎么敲、谁在敲、哪些命令在任何状态下都回话、为什么改了配置当场没反应。

命令的形状：<前缀>/<函数名> <参数>

<前缀>/<函数> <参数>框架约定的命令行形状通用
前缀
前缀 = 插件名 = jar 名：AiAgentV4.jar → AiAgentV4/status，jar 改名 ai.jar 就是 ai/status（src\sair\v4\V4Activity.java）。本页下文一律写 ai/…。
函数名
大小写不敏感、两端空白裁掉：分发口进来先 trim().toLowerCase()，参数串同理（src\sair\v4\term\Cmd.java）。ai/STATUS ≡ ai/status。
参数
整串原样交给命令自己切分，多参命令按空白切 N 段（napcat send 切 3 段 src\sair\v4\term\Cmd.java；prompt inject 切 3 段）。带空格的值放最后一段。
回显
默认落控制台主输出框；对话正文另有一路落点（有面板进面板，没有则回落主输出框），取法在 src\sair\v4\term\Cmd.java。
不抛异常
整条分发被 catch (Throwable) 兜住：任何命令炸掉只收敛成一行可读失败 + "可用 help/status/tools/config 继续操作"，可以继续敲下一条（src\sair\v4\term\Cmd.java）。未知命令也只回 未知命令：X（输入 ai/help 看命令表）。

谁在敲：控制台调用者恒为主人

调用者由 caller() 现造：取 conf.masterQQ() 交给 Caller.console(long)，配置还没加载时主号按 0（src\sair\v4\term\Cmd.java）。Caller 类注释第一段就是这条口径：本地控制台交互 ≡ QQ 中的主人交互，console() 造出来的就是主人（src\sair\v4\auth\Caller.java）。命令表里的同一句话是"主人 = MASTER，工具一律全放行"（src\sair\v4\term\Cmd.java）。两个后果：ai/tools 不带参数按这个调用者筛；ai/chat 就是主人说话那条链路（类注释）。

永远可用的四条：help / status / tools / config

硬要求写在类注释里：不依赖模型 / 数据库 / NapCat 的命令永远可用（src\sair\v4\term\Cmd.java）。装配没跑到、跑到一半、整块失败，这四条照常回话。

命令没装配起来时怎么回话
ai/help 契约是"永不抛异常、永远返回非空数组"：连构造都失败也有一张静态兜底表（降级命令表三行）。
ai/status 回"status 不可用：基板没装配起来（+ 缺什么）"，并提示 ai/start 能让它加载并运行。
ai/tools 注册表还没建就报"工具面还没装配：<原因>"，并说明基板工具在装配的「工具面」那一步注册、其余工具在外挂扫描之后陆续出现。
ai/config 装配没走到第①步时用壳配置直接按数据根读 config.json：总览 / 单键 / set 全部照常应答，回执额外说明"基板未启动：这份配置一个键都还没加载"。

"没启动"是正常状态，不是故障：ai/start 之前基板就是不工作的 —— 没有库、没有工具面、没有 NapCat 连接。这时 ai/status 第一句是 未启动（ready=0 reason=not_started）：基板还没跑起来。，随后给配置文件路径与待生效键清单（src\sair\v4\term\Cmd.java）。

改配置为什么不立刻生效

只有一条口径：改文件 ≠ 生效。让文件里的值进到跑着的基板里，只有 ai/start（没在跑）或 ai/restart（已经在跑）两条路（src\sair\v4\term\Cmd.java）。

  1. ai/config set 只写文件：调 conf.fileSet(键, 值)（src\sair\v4\term\Cmd.java）。写文件的纪律（最小改动、凭据键现加密、首次先落默认值）在 src\sair\v4\Conf.java、实现 。
  2. 有没有人读它由已知键表说了算：Conf.knownKeys()（src\sair\v4\Conf.java），表里每个键都有活着的消费者。不在表里的键写进去不会有任何行为变化，回执会点明（src\sair\v4\term\Cmd.java）。
  3. 待生效是唯一能看见"我改了但没生效"的地方：Conf.pendingKeys() 逐键比对文件值与已生效值（src\sair\v4\Conf.java、判据 isPending()）。ai/status 与 ai/config 总览都会标它。
  4. 老那张"改了要重启"的键表已整条退休，不再有两把尺子（src\sair\v4\Conf.java）；刻意保留的例外只有一个：Conf.set() 仍是运行期内部代码"改生效值"的口。

因此：ai/config set …、ai/napcat on|off、ai/napcat relay on|off 的回执都带同一句 —— "未生效 —— 要 ai/start；已在运行则 ai/restart"（共用回执 src\sair\v4\term\Cmd.java）。

已删除的"通道"类命令

敲 execs / execq / execfc / orchestrate 不回"未知命令"，而是告诉你这四个名字属于已删除的「通道」概念：V4 只有一条入口，直接用 ai/chat <内容>；后面还带了内容就顺手当 chat 发出去（src\sair\v4\term\Cmd.java）。

生命周期

三、生命周期：start / restart 与框架四条

这两条是"基板开始工作"与"按新配置重装"的唯一入口。动作不在命令里 —— 命令只说，动作与状态机在组件里跑。

ai/start用法：ai/start，不接受参数唯一的加载并运行
参数
无。后面跟任何文字都被忽略（分发口只按函数名匹配，参数串不参与，src\sair\v4\term\Cmd.java）。
效果
未加载 → 读 config.json 并跑完整 19 步装配；已在运行 → 只回一句"已在运行"，一个动作都不做；已经有一条装配/重启在跑 → 明确拒绝（不并发）。装配跑在基板自己的守护线程上，进度一行行打在控制台，命令立刻返回（src\sair\v4\term\Cmd.java）。
四种回话
对应生命周期面的四个结果值（src\sair\v4\term\Cmd.java）：ACCEPTED 启动已受理 · RUNNING 已在运行（幂等，不做任何动作）· BUSY 装配中（本次拒绝）· UNAVAILABLE 组件已卸载（要重装/重载插件，或重启 SFW）。
依赖
组件入口（生命周期宿主）。宿主为 null 时退化成"同步装配一次"，回话里说明本环境没有生命周期宿主（src\sair\v4\term\Cmd.java）。宿主实现者是插件组件类 src\sair\v4\V4Activity.java，它把 start() 写成幂等三态。
注意
已在运行时不会重启，但回话会说清怎么才能生效：ai/restart（src\sair\v4\term\Cmd.java）；文件里有待生效键时结尾再补一行 ＊ pending=… 点名。
注意
命令表本身（help/status/tools/config）不在这里、也不在装配路径上：没人敲 start 之前基板就是不工作的（src\sair\v4\V4Activity.java）。
ai/restart用法：ai/restart，不接受参数会停一次旧基板
效果
停旧基板（收库 / 收监听 / 收线程池）→ 重读 config.json → 重新跑 19 步装配，进度照旧打在控制台（src\sair\v4\term\Cmd.java；装配线程里的三步动作 src\sair\v4\V4Activity.java）。
回话
ACCEPTED 重启已受理 · BUSY 装配中（拒绝）· UNAVAILABLE 组件已卸载（src\sair\v4\term\Cmd.java）。
依赖
组件入口。没有宿主时 restart 直接拒绝并说明本环境没有生命周期宿主（src\sair\v4\term\Cmd.java）—— 这一点与 start 不同。
不并发
调用线程只做两件便宜事：新建空壳基板 + 换掉命令表 + 起装配线程；"同时只允许一条装配/重启"由组件里一个原子名额守着（src\sair\v4\V4Activity.java、判据 占用）。
注意
重启只收基板，不收观测面：两个调试口与落盘不归它管（src\sair\v4\term\Cmd.java）。重启换的是新基板，观测面每次现取活基板，所以之后仍报同一对端口与新的活基板（src\sair\v4\V4Activity.java）。

装配：19 步，跑在守护线程上

事实值 / 行为
总步数常量 19，各处台账与进度行都用它
步骤清单19 行 step("名字", …)：数据目录与配置 → 空数据骨架 → 六库 → 权限 → 提示词 → 工具注册表 → 模型客户端 → NapCat 连接 → 上下文装配 → 外挂库 → 回合调度器 → Agent → 心跳 → QQ 网关 → 基板工具面 → 外挂扫描 → NapCat 监听 → 文件外链中转 → 心跳启动
进度行第 x/19 步 <步骤名>，已耗时 …ms；装配线程已起但没到第一步时给"第 0/19 步（装配线程已起，正在准备）"
在谁的线程上守护线程 v4-boot；调用线程（可能是界面线程）只做"搭壳 + 起线程"
某一步失败只让那项能力缺失，记下第一个失败的步骤名与原因，装配继续；ai/status 打印失败台账

受理与进度不打架：投递被受理之后、装配线程真正跑起来之前有一个毫秒级窗口，那个窗口里 ai/status 已经会说"加载中：第 0/19 步" —— 不许出现"命令说受理了、状态说没开始"，所以"有人要它跑"的标记在起线程之前就置位（src\sair\v4\V4Activity.java）。

框架四条：exit / close / open / uninstall

这四条不在分发口里（src\sair\v4\term\Cmd.java 起没有任何分支匹配它们），是框架自己的控制台命令；命令表只负责列出它们并说明语义。

命令命令表里的原话组件侧落到哪里
ai/exit框架转发到组件 exit()：停基板（不改配置、不卸载插件；之后可再 start）清掉基板与命令表引用、标记卸载、观测面随壳卸载（停两个口 + 关落盘句柄 + 注销控制台捕获）；基板还在装配时只做标记，交装配线程收口（src\sair\v4\V4Activity.java）
ai/close / ai/open框架语义：停止 / 恢复「接受命令」（close 后只有 exit/close/open/uninstall 进得来）框架侧行为，组件不参与：close 期间基板照旧在跑，只是命令进不来
ai/uninstall框架级卸载：卸载前自动 exit() + close()（卸载后要重装才可用）先走上面的 exit() 路径收基板与观测面，再由框架卸载插件

ai/exit 不是"退出程序"：它只停基板。基板停下后调试口关闭，而 JVM 进程仍然活着 —— 在没有控制台的场景下无法"再 start"。这是当前实现的行为，源码里没有计划修改的痕迹。正确关停方式与完整理由见第十三节。

卸载之后还能敲命令吗：能。卸载后命令表还在（降级命令表：help 仍非空、其余给"未装配"的可读回话），并且不会因为有人再问一句就自动装配；start/restart 是"显式要它跑"，会重新装配 —— 但这只对还够得着控制台的场景成立（src\sair\v4\V4Activity.java）。

对话

四、对话命令：chat / stop / reset

控制台里的 chat 就是主人说话 —— 与 QQ 侧的主人消息走同一条链路。这一节写清它的前置判断、等待行为与三条命令的回显。

ai/chat <内容>别名：ai/say <内容>主人说话那条链路
参数
<内容> 必填，整串原样当这一轮的用户输入（含空格）。空参数只回 用法：chat <要说的话>，不做别的动作（src\sair\v4\term\Cmd.java）。
效果
组上下文 → 提交一个回合给回合线程池 → Agent 跑。正文（含流式）走对话落点，主人这句话也写进对话面板（否则面板里只有 AI 一侧，读起来像独角戏：src\sair\v4\term\Cmd.java）；随后用户这句与她的回话都落库。
依赖
模型 + apiKey + 上下文装配 + 六库 + 回合调度器 + Agent。五道前置判断，任一道不通过都只回一句明确的话、不抛异常：① 装配中（且没失败过）→ 回外挂文案的「初始化中文案」；② 装配未齐备（Agent/上下文/六库/调度器任一为 null）→ 说清缺什么并让你先看 status；③ 回合队列已关闭（基板已 stop）→ 提示重启组件；④ 模型客户端未装配或 apiKey 未配置 → 给出确切命令 ai/config set apiKey <你的 key> 并顺带报当前 api 地址与解析后的模型名；⑤ 队列已满 → 不提交并告警（src\sair\v4\term\Cmd.java）。
等待上限
键 chatTimeoutMs，出厂默认 180000 ms（src\sair\v4\Conf.java，读口）。超时只回"本轮仍在后台跑，控制台不受影响"，并提示可用 ai/stop 中断或看队列长度（src\sair\v4\term\Cmd.java）。队列堵死也不会把控制台永久卡住。
注意
在控制台手敲时命令当场就还给你：控制台命令跑在界面线程上，输入框、面板重绘、控制台输出也在那条线程上 —— 在这里等一轮就是界面整块卡住。所以判据是"调用线程是谁"：界面线程上只提交、不等（正文由落点流式打出去，摘要行由回合线程补）；脚本 / 其它后台线程照旧阻塞等待，顺序语义不变（src\sair\v4\term\Cmd.java）。
注意
回合结束那行摘要 [本轮 N 轮 · Nms] 默认不打：要看得把 logConsole 加上 turn（出厂默认 tool,model，src\sair\v4\Conf.java；判据 src\sair\v4\term\Cmd.java）。装配中的那句提示是外挂文案（prompts/tools-index.md 的「初始化中文案」），缺键时只报缺哪个键、不自己编一句。
ai/stop用法：ai/stop，不接受参数中断输出
效果
请求中断当前输出，回 已请求中断当前输出（停了 N 个在跑的回合）（src\sair\v4\term\Cmd.java）。
语义差别
控制台 = 主人，所以停全部；QQ 侧同一个命令只停自己那个会话的回合（src\sair\v4\term\Cmd.java，调用 stop(null, true)）。
依赖
Agent。没装配时回 stop 不可用：Agent 未装配（<缺什么>），不抛异常。
ai/reset用法：ai/reset，不接受参数只清控制台会话
效果

注意事项

十三、注意事项与坑

前十二节是"怎么用"，这一节是"容易踩的地方"。两条最要紧：群消息只有被 @ 才触发；真正要关停时，用 /exit 比 ai/exit 稳当。

一、群消息只有被 @ 才触发

这条口径在网关里只有一个判据方法：QqGateway.shouldAnswer(Ev, Caller)。方法体三行 —— 空调用者直接否，私聊一律回，群里只认被 @：

javasrc\sair\v4\QqGateway.java
public boolean shouldAnswer(Ev ev, Caller c) {
    if (c == null) return false;
    if (ev.isPrivate()) return true;      // 私聊 = 直接找它
    return ev.atSelf();                   // 群里：只认被 @
}
要点说明
判断分支 方法所在分支：群聊（ev.isPrivate() 为假）走到最后一行 return ev.atSelf(); —— 这一处就是"群里只有 @ 才触发"的全部实现；私聊在上一个分支直接 return true。
谁在用这个判据 入站处理链在"插件投票没人表态、且本条没有否定票"之后调它：判否就记一行 skip reason=not_addressed session=…（非主人/非私聊/未@） 并直接结束，不产生模型调用。
主人也没有豁免 同一方法上方的注释写明：早先"主人一律返回"的写法让主人在群里说任何话都被回，现在口径统一 —— 群里要么 @ 它，要么由外挂层投票放行，主人也一样。
只有 @ 一下、没有文字 无文本且除 @ 之外没有内容段时，若没被 @ 就直接跳过；被 @ 了则带着上下文起一轮（输入文案是外挂文案里的「被单@时的输入」，缺键则报缺键且不发这一轮）。
控制台不受它管 控制台命令不是 QQ 消息，不经过这个判据：ai/chat 是主人直接说话（见第四节）。

二、真正要关停：用 /exit，或按精确 pid 杀进程

先把话说死：ai/exit 不是"退出程序" —— 它只停基板。基板停下之后调试口会关闭，而 JVM 进程仍然活着；于是在没有控制台的场景下无法"再 start"。这是当前实现的行为，源码里没有任何"计划修改"的痕迹。

链路发生了什么
ai/exit 的命令表文案 "框架转发到组件 exit()：停基板（不改配置、不卸载插件；之后可再 start）" —— 注意最后半句的前提：要有控制台才谈得上"再 start"。
组件收到 exit() 清掉基板与命令表引用 → 标记卸载 → 把观测面也一起收掉（停两个口 + 关落盘句柄 + 注销控制台捕获）→ 基板还在装配时只做标记，交给装配线程跑完自己收口。
两个口怎么没的 收观测面的第一件事就是停两个口，凭据文件 debug-port.json 随停止而删 —— 它是"口在听"的运行现场凭据。
进程为什么还在 调试口源码注释把结论写死了：本组件路径不结束进程（全程 0 处 System.exit）；真退出要另走 ai/exit → 组件 exit() → 停基板，那也只是"停基板"，同样不结束 JVM；端口 / 日志 / 基板会关掉，进程还在。
实测复核 全仓检索 System.exit：1 处命中，且该命中是一行注释（就是上面那段说明自己）—— 源码里没有任何一处真的结束 JVM。
退出之后的命令表 卸载后命令表还在（降级命令表：help 仍非空、其余给"未装配"的可读回话），也不会因为有人再问一句就自动装配；start / restart 会重新装配 —— 但这只对还够得着控制台的场景成立。

正确做法：两条

① 用框架控制台的 /exit

框架自带文档把 /exit 的定义写得很直白：退出框架 / 退出 SFW —— 示例行 /exit # 退出框架（C:\Sair\SairFrameWork\readme\pages\plugin-dev.html），命令表行 /exit → 退出 SFW。它关的是框架自己的窗口，进程随之结束。

同一条路在调试输出口也留了入口：口上敲 exit / /exit 会走"关框架"那条调用 → 框架关窗（src\sair\v4\dev\DebugPort.java、命令表）。

② 按精确 pid 杀进程

框架是用 javaw 起的：run.bat 的内容是 start 8x64\bin\javaw -jar SFW.jar %*（实测读取 C:\Sair\SairFrameWork\run.bat）。javaw 没有控制台窗口，所以"关掉黑框"这条路不存在。

要做的是先定位到这一个 pid再按 pid 结束它：查 javaw.exe 进程列表、核对命令行 / 启动时间，确认是这一个实例之后再结束。按进程名批量结束容易误伤 —— 同一台机器上可能有别的 java / javaw 实例。

把三条名字很像"关机"的命令分清：ai/exit = 停基板 + 收观测面；ai/close = 只让命令进不来（基板照旧在跑）；ai/uninstall = 先 exit() + close()，再由框架卸载插件。三条都不结束 JVM 进程。

三、其它容易踩的地方

控制台命令跑在界面线程上凡"要等"的动作都不许在这里等已按调用线程分流
现象
输入框、面板重绘、控制台输出都在同一条界面线程上；命令里只要阻塞几秒，界面就整块卡住。
现状
ai/chat 在界面线程上只提交、不等（正文由落点流式打出去，摘要行由回合线程补），脚本 / 其它后台线程照旧阻塞等待（src\sair\v4\term\Cmd.java）；ai/napcat send 把网络往返丢给后台线程。
注意
ai/store vacuum、ai/store optimize、ai/store maintain 没有这层分流 —— 它们直接在调用线程上跑数据库操作，库大时界面会等你敲完的那条命令。
三类命令"只改文件"改完不生效是设计，不是故障回执里已写明
哪三类
ai/config set、ai/napcat on|off、ai/napcat relay on|off —— 回执统一带"未生效 —— 要 ai/start；已在运行则 ai/restart"（共用回执 src\sair\v4\term\Cmd.java）。
怎么确认清空了
ai/status 在任何状态下都给待生效清单：加载中给个数、已就绪总是打一行（哪怕是 pending=0），好让人看见清单变空了（src\sair\v4\term\Cmd.java）。
例外
提示词正文有自己的热重载（ai/prompt reload），见第十二节。
不在已知键表里的键写了也没用回执会点明
判据
已知键表 = Conf.knownKeys()（src\sair\v4\Conf.java 起），表里只登记"有人读"的键；不在表里的键照写进文件，但不会有任何行为变化（回执原文 src\sair\v4\term\Cmd.java）。
注意
旧的口径类键若还留在 config.json 里，启动时只提示一行"已退休"，不报错、不参与判定（src\sair\v4\Conf.java）。
调试口开了不等于基板在跑两个口与基板相互独立看 substrate=
怎么分清
ai/debug status 那行事实里有 substrate=running|not_started（未跑时带 reason=）；两个口不缓存基板：ai/start 之后它们报的就是那台活基板（src\sair\v4\term\Cmd.java、src\sair\v4\V4Activity.java）。
注意
ai/debug off 只停两个口：不停落盘、不删任何日志文件；反过来停基板也不会关这两个口（src\sair\v4\term\Cmd.java）。
无法撤销的几条敲下去就生效，没有确认步骤想清楚再敲
清单
ai/perm reset（清空全部好感度记录 src\sair\v4\term\Cmd.java）· ai/prompt clear（清空全部注入）· ai/reset（清控制台会话历史）· ai/store vacuum（回收空闲页且期间独占数据库）· ai/uninstall（框架级卸载，卸载后要重装才可用）· ai/store import（往库里加行，不是替换）。
注意
这些命令都没有确认口，也不产生备份文件。数据库文件本身可以离线复制一份当保险。
已经不存在的东西别照着老习惯敲未实现 / 已删除
已删除
perm levels / perm setlevel（旧档位体系的读写口，整组删除，src\sair\v4\term\Cmd.java）；execs / execq / execfc / orchestrate（已删除的「通道」概念）；debugPort / debugToken / debugSimPort / debugSimulate 四个配置键（src\sair\v4\Conf.java）；config reload 的热重载语义（命令还在，只回一句"已退休"，src\sair\v4\term\Cmd.java）。
未实现（不承诺）
控制台里没有这些口子，源码里也没有对应分支：定时唤醒的新增 / 取消；权限账本的写入（授权 / 撤销）；失败步骤的自动重试；ai/exit 之后"没有控制台也能再 start"的远程入口；ai/debug on 指定端口。要用到它们，只能走上面写明的既有路径。

一句话总括：改文件类命令（config set / napcat on|off / napcat relay on|off）改完要 ai/start 或 ai/restart；看状态类命令（help / status / tools / config / acl / debug status）任何状态下都能敲；要真关停用框架控制台的 /exit 或按精确 pid 结束进程 —— ai/exit 到不了那一步。
